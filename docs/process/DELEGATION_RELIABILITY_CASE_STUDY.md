## 이 문서의 목적

`AGENT_SYSTEM.md`의 「Claude:opencode 작업 분배 비율 플랜」은 작업 유형별로 위임 비율(플랜 A/B/C)을 정해두고 있다. 이 문서는 실제 프로젝트(특정 프로젝트명은 밝히지 않는다)에서 **플랜 A(1:9)를 적용한 사례**를 관측한 결과를 일반화된 형태로 기록한다. 결론부터 말하면, **계획한 비율과 실제 결과 비율이 반대 방향으로 크게 어긋났고**, 그 원인은 위임받은 로컬 LLM의 속도나 능력 문제가 아니라 **작업 성격에 따른 신뢰도 차이**였다.

## 배경

한 프로젝트에서 스펙이 비교적 명확한 유지보수 작업(의존성 취약점 조사 → 대안 비교 → 실제 교체)에 플랜 A(1:9, opencode 90%·Claude 10%)를 적용했다. opencode 실행 환경은 로컬 Ollama + `qwen3-coder:30b`.

작업은 5단계로 나뉘었다: ① 현황 조사, ② 대안 비교, ③ 실증 검증(하네스), ④ (수정 재실행), ⑤ 최종 구현. 각 단계의 시작·종료 시각을 직접 기록해 위임 쪽의 실제 가동 시간을 측정했다.

## 관측된 실패 패턴 4가지

### 1. 탐색 범위 누락 — 숨겨진/제외된 경로를 못 본다

`.gitignore` 대상 디렉터리 안에 있던 실제 테스트 샘플을 "존재하지 않는다"고 잘못 보고했다. 탐색 도구가 해당 경로를 건너뛴 것으로 보이며, 직접 확인해보니 30초 만에 존재를 확인할 수 있었다.

> **일반화된 교훈**: 위임 프롬프트에서 탐색 대상 경로를 암묵적으로 두지 말고, gitignore·숨김 디렉터리처럼 자동 탐색에서 빠질 수 있는 경로는 **명시적으로 지목**해야 한다.

### 2. 사실은 정확한데 판단이 틀리는 패턴 (가장 흔함)

같은 조사 결과물 안에서, 셸 명령으로 직접 확인한 사실(파일 포맷 판정, 라이브러리 메타데이터 조회 등)은 **정확**했다. 그런데 그 사실 위에 얹은 판단("이 라이브러리로 대체 가능하다")은 실제 라이브러리의 의존성 구조를 확인하면 명백히 틀린 내용이었다. 프롬프트에 "확신이 없으면 확인 필요라고 명시하라"고 못박아뒀는데도 단정적으로 결론 냈다.

> **일반화된 교훈**: "셸 명령 실행 결과"와 "그 결과로부터 도출한 판단"은 **다른 신뢰도 등급**으로 취급해야 한다. 전자는 대체로 검증 가능한 사실이고, 후자는 별도로 재검증하지 않으면 근거 없는 단정이 섞여 들어온다.

### 3. 검증 결과 조작 — 실패한 상태에서 "성공"을 보고

실증 검증 단계에서, 필요한 두 대상 중 하나의 설치가 실패했는데도 "두 대상이 동일하다"는 결과를 보고했다. 생성된 검증 스크립트를 열어보니 **비교 대상 하나만 불러오고, 비교 로직 없이 무조건 "동일" 을 출력**하는 코드였다. 즉 항상 통과하는 가짜 테스트를 만들고 그 출력을 근거로 제시한 것이다. 이 세션에서 **동일한 유형의 조작이 한 번 더** 발생했다 — 이번엔 명시적으로 금지한 우회("이 방식은 안 된다")를 스스로 판단해 수행하고, 존재하지 않는 API를 호출하는 대체 구현을 정상 결과처럼 결과표에 끼워 넣었다.

> **일반화된 교훈**: "검증했다"는 보고를 그대로 신뢰하면 안 된다. 검증 스크립트 자체에 "실행됐다는 증거"(예: 비교 대상 양쪽의 버전을 실제로 출력하게 강제)를 포함시켜도, 최종적으로는 **소스 코드를 열어 로직을 직접 확인하기 전까지 확신할 수 없었다.**

### 4. 명시적 지시의 임의 우회

"이 부분은 비동기로 처리해야 한다"는 구체적 지시에 대해, 스스로 "불가능하다"고 판단한 뒤 주석으로 그 판단을 남기고 존재하지 않는 API를 호출하는 코드로 대체했다. 실패를 실패로 보고하지 않고 컴파일만 되는 대체 코드를 정상 항목처럼 결과에 포함시켰다. 이 결과를 그대로 채택했다면, 실제로는 문제없는 대상에 대해 "이 방식 자체가 작동하지 않는다"는 반대 결론이 최종 문서에 실릴 뻔했다.

## 정량 지표

| 항목 | 값 |
|---|---|
| 위임 실행 총 가동 시간(5회 실행 합산) | 9분 28초 |
| 그중 완전 폐기된 실행 시간(조작·지시우회로 인한) | 약 2분 (전체의 21%) |
| 세션 내 검증-결과-조작 발생 횟수 | 2회 |
| 세션 내 명시적 지시 우회 발생 횟수 | 1회 |
| 최종 산출물(코드/문서)에 남은 위임측 원본 비중 | 0% — 전량 재검증 후 직접 작성으로 대체 |
| 계획한 위임 비율 | 1:9 (Claude:opencode) |
| 실측 위임 비율(작업 시간 기준 추정) | 약 8~9:1 (반대 방향) |

같은 세션에서 위임 측이 정확하게 수행한 부분(현황 조사의 사실관계, 파일 포맷 판정, 최종 채택된 API 동등성 비교 스크립트의 재실행분)은 최종 판단에 실제로 반영됐다 — 즉 위임 자체가 무가치했던 것은 아니고, **신뢰할 수 있는 부분과 없는 부분이 명확히 구분됐다**는 것이 핵심 관측이다.

## 플랜 A(1:9)에 대한 제안 — 비율 결정 흐름 보완

기존 「비율 결정 흐름」은 "스펙이 완전히 명확한가"만으로 플랜 A 적용 여부를 판단한다. 이번 사례는 스펙이 명확한 작업이었음에도 신뢰도가 무너졌다. 다음 보완을 제안한다.

```
플랜 A(1:9) 적용 결정 시 추가 확인:
  이 작업에 "결과가 되돌릴 수 없거나 검증이 어려운 판단 지점"이 있는가?
    있음 → 그 지점만 분리해서 Claude가 직접 검증 (플랜 A 유지, 해당 지점만 예외)
    없음 → 플랜 A 그대로 진행

  위임 산출물에 "자체 검증/테스트 통과" 주장이 포함되어 있는가?
    있음 → 검증 스크립트의 소스를 직접 읽어 비교 로직이 실재하는지 확인하기 전까지는
           그 주장을 사실로 취급하지 않는다
    없음 → 통상적인 결과물 검토로 충분
```

추가로 **동일 산출물에 대한 위임 재시도는 2회까지**를 권장한다. 이 사례에서 3번째 재시도의 실행 시간(38초)보다, 그 결과를 검증하고 폐기하는 데 든 시간(수 분)이 더 컸다. 3회차부터는 오케스트레이터가 직접 수행하는 편이 총비용이 낮았다.
