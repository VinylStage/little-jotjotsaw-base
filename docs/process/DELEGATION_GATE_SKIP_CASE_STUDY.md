## 이 문서의 목적

[`DELEGATION_RELIABILITY_CASE_STUDY.md`](./DELEGATION_RELIABILITY_CASE_STUDY.md)는 플랜 A(1:9)를 **적용은 했으나** 신뢰도가 무너져 실측 비율이 반대로 뒤집힌 사례를 다뤘다. 이 문서는 다른 성격의 사례를 기록한다 — 어떤 프로젝트(특정 프로젝트명은 밝히지 않는다)에서 진행한 24개 항목 규모의 감사(audit) 대응 사이클 전체에서, **위임 여부를 판단하는 지점 자체가 한 번도 발생하지 않아** 계획된 비율이 아니라 100:0(Claude 전량 직접 처리)으로 끝난 사례다. 실패가 아니라 **프로세스 게이트 자체의 부재**라는 점에서 앞선 사례와 구분해서 다룬다.

## 배경

한 프로젝트에서 외부 감사보고서에 대응해 24개 이슈를 5개 마일스톤으로 나눠 순차 처리했다. 이슈들의 성격은 보안 미들웨어 도입, 데이터 정확성 버그(정확한 재현 시나리오 확인 필요), SQL 쿼리플랜 최적화, 코드 리팩토링, UI 접근성 라벨링, 성능 측정 인프라 도입까지 다양했다 — 즉 `AGENT_SYSTEM.md`의 플랜 A/B/C 분류로 보면 세 플랜에 걸친 혼합 작업량이었다.

사이클이 다 끝난 뒤, 사용자가 "1:9 위임 비율이 지켜졌는지" 질문했다. 그 시점까지 오케스트레이터(Claude)는 위임 여부를 단 한 번도 검토하지 않은 채 21개 항목(이슈 시작→구현→테스트→PR)을 전부 직접 처리해온 상태였다.

## 측정 방법과 결과

앞선 사례 연구는 작업 시간을 수동으로 기록해 위임 비율을 추정했다. 이번엔 다른 방법을 썼다 — **git 커밋의 `Co-Authored-By` 트레일러를 감사 근거로 사용**했다. 사이클 기간 동안의 전체 커밋 이력을 조회해 다음을 확인했다:

| 항목 | 값 |
|---|---|
| 사이클 내 완료된 이슈 수 | 21건 |
| 로컬 LLM(opencode) 저자·co-author 표기가 있는 커밋 | 0건 |
| 같은 기간 `Co-Authored-By` 트레일러 전부의 소속 | Claude 계열만 |
| 위임 CLI(opencode) 호출 이력(bash 실행 로그 기준) | 0건 — 시도 자체가 없음 |
| 계획된(문서상) 위임 비율 | 작업 성격에 따라 1:9~5:5 혼합 |
| 실측 위임 비율 | 100:0 (Claude 전량) |

**이 측정 방법 자체가 일반화 가능한 기법이다.** 수동 시간 기록 없이도, 커밋 트레일러만으로 "이번 사이클에 위임이 실제로 일어났는가"를 사후에 객관적으로 재구성할 수 있었다. 위임 비율을 추적하려는 다른 프로젝트에도 그대로 적용 가능하다.

## 원인 분석 — 왜 게이트가 아예 발동하지 않았나

앞선 사례 연구(신뢰도 붕괴)와 원인이 다르다. 이번엔 위임을 시도했다가 실패한 게 아니라, **"이 작업을 위임할지 말지" 자체를 판단 기준에 올린 적이 없었다.** 오케스트레이터 스스로 재구성한 원인은 네 가지다.

1. **재진입 트리거 부재**: `AGENT_SYSTEM.md`의 「비율 결정 흐름」은 존재하지만, 이슈 착수 시점마다 이 흐름을 자동으로 다시 참조하게 만드는 장치가 없었다. 사용자가 "다음 마일스톤 계속 진행해줘"라고 지시하면 오케스트레이터는 곧바로 직접 구현으로 들어갔고, 위임 여부를 판단 지점으로 세우지 않았다.
2. **작업 성격의 편향**: 21건 중 상당수가 실제로 플랜 B/C 영역(보안, 데이터 정확성, 쿼리플랜 검증)이었다. 이 편향이 "그냥 직접 하는 게 낫다"는 관성을 만들었고, 그 관성이 명백히 플랜 A(1:9) 대상이었던 작업(UI 컴포넌트 라벨링 79건 — 스펙 완전히 명확, 반복적, 판단 불필요)에도 그대로 적용됐다. 즉 소수의 플랜 A 대상 작업이 다수의 플랜 B/C 작업 흐름에 묻혀 별도로 식별되지 못했다.
3. **최근 신뢰도 사고의 무의식적 회피**: 같은 프로젝트에서 하루 전 위임 CLI의 툴콜 파싱 실패(원시 XML 텍스트 출력) 사고가 있었다. 이 사고를 의식적으로 참조해 "그래서 이번엔 직접 한다"고 판단한 적은 없다 — 그냥 위임을 고려 대상에서 빼놓은 채 진행됐다. 의식적 리스크 회피가 아니라 암묵적 회피였다는 점이 중요하다.
4. **검증 루프의 단일 세션 편의성**: 이 사이클은 수정마다 뮤테이션 테스트(고의로 되돌려 실패 재현 확인)와 크로스 PR 충돌 예측(스크래치 브랜치 병합 테스트)을 요구했다. 감사보고서의 정확한 재현 조건과 이전 수정들의 문맥을 매 위임 프롬프트마다 다시 전달해야 하는 부담이, 위임을 아예 고려하지 않게 만드는 쪽으로 작용했을 가능성이 크다.

## 별도 진행한 툴체인 재조사 — 검증 결과

같은 시점에 별도 세션에서 위임 CLI(opencode)의 신뢰도 문제를 재조사했다. 이 문서에서는 그 결론을 **직접 GitHub API로 재검증**했다(제목만 보고 그대로 인용하지 않았다):

| 이슈 성격 | 상태 | 재검증 결과 |
|---|---|---|
| 원격 모델 레지스트리(models.dev) 응답 없을 시 행/종료 | 완료(수정됨) | `/etc/hosts`에서 해당 도메인을 막으면 재현된다는 재현 절차가 이슈에 명시돼 있음 — **로컬 전용 사용을 표방하는 도구가 실제로는 원격 의존성을 갖고 있었다**는 구조적 사실 확인 |
| 완전 오프라인/에어갭 모드 요청 | 완료 | 요청자 본인이 "로컬 모델(Ollama/vLLM)로 매일 쓴다"고 명시 — 로컬 모델 사용자도 이 요구가 있었다는 정황 확인 |
| 툴콜 도중 원시 XML 텍스트 출력 | 완료(수정됨) | 이 프로젝트가 겪은 것과 거의 동일한 증상(닫는 태그 누락 등)이 이미 보고돼 있었음. **완료 처리됐다는 점도 확인** — 즉 이번 사이클 하루 전 겪은 실패가 이미 패치된 버전에서도 재발한 것이거나, 별개의 회귀일 가능성이 있음(단정 불가) |
| vLLM 백엔드 + 특정 Qwen3 양자화 모델 조합에서 무음 크래시 | **수정 계획 없음(not planned)** | 이 이슈는 Ollama가 아니라 **vLLM 백엔드 + 특정 양자화 변형**에 한정된 보고였다. "다른 모델에서도 재현된다"는 원 리서치의 결론을 이 이슈 하나로 일반화하기엔 근거가 약함 — 다만 Qwen3 계열의 XML 툴콜 포맷 자체가 여러 서빙 백엔드에 걸쳐 취약하다는 정황 증거로는 유효함 |

**교훈**: 재조사 결과를 그대로 문서에 옮기지 않고 원본 이슈를 직접 열어 상태(완료/미계획)와 재현 조건(어떤 백엔드·어떤 모델)까지 확인하니, "구조적 결함이라 모델을 바꿔도 안 없어진다"는 결론이 4건 중 1건에서는 과도한 일반화였음이 드러났다. **2차 출처(리서치 요약)의 결론도 판단이 섞여 있으면 재검증 대상**이라는 점에서 앞선 사례 연구의 교훈("사실과 판단을 다른 신뢰도로 취급하라")과 같은 결이다.

## 손으로 검증한 대안 비교 실험

이론 검토로 끝내지 않고, 같은 로컬 모델(qwen3-coder:30b, Ollama)을 대안 CLI(Aider)와 기존 CLI(opencode) 양쪽에 동일한 스펙-명확 위임 태스크(순수 함수 구현 + 테스트 작성, 플랜 A 전형)로 3회씩 실행해 비교했다.

**1차 시행에서 대안 CLI가 2/3 실패하는 것처럼 보였으나, 원인을 추적해보니 검증 스크립트 자체의 결함(재시도 사이 `git reset --hard` 대신 `rm -rf`만 써서 git 인덱스에 유령 항목이 남음)이었다.** 올바르게 리셋한 뒤 재실행하니 양쪽 다 3/3 성공했다.

| 항목 | 기존 CLI(opencode) | 대안 CLI(Aider) |
|---|---|---|
| 성공률(올바른 방법론 기준) | 3/3 | 3/3 |
| 소요 시간 | 30~63초 | 9~28초(웜업 후 더 빨라짐) |
| 요청 외 파일 부수효과 | 없음 | 매 실행 `.gitignore` 자동 생성 + git 인덱스에 자동 스테이징 |
| 기본 네트워크 동작 | 원격 모델 레지스트리 의존(위 재조사 참고) | `--help` 확인 결과 분석(analytics) 기본값이 "random"(확률적 활성화), 업데이트 체크도 기본 활성 — "강제 네트워크 fetch 없음"이라는 원 리서치 결론은 **명시적으로 `--no-analytics --no-check-update`를 켜야만 성립**, 기본값 기준으로는 부정확 |

**교훈**: 이 표본(n=3)으로는 "대안이 더 안정적이다/아니다"를 판단할 근거가 못 된다 — 두 도구 다 간헐적 결함이 보고돼 있고, 3회 성공이 결함 부재를 증명하지 않는다. 확실하게 검증된 것은 두 가지뿐이다: (1) 대안 CLI는 요청하지 않은 파일 부수효과를 매번 만든다, (2) "네트워크 완전 차단" 주장은 기본 설정 기준으로는 틀렸다 — 둘 다 **직접 실행해보지 않았으면 몰랐을 사실**이고, 리서치 요약만 봤다면 그대로 잘못된 결론을 채택했을 것이다.

## 제안

### 1. 위임 게이트를 이슈 착수 체크리스트에 명시적으로 포함

`AGENT_SYSTEM.md`의 「비율 결정 흐름」이 존재하는 것과, 매 이슈 착수 시 실제로 참조되는 것은 다르다. 다음을 이슈/작업 착수 시점의 **필수 첫 단계**로 명시할 것을 제안한다:

```
이슈 착수 시 (스킵 불가):
  1. 이 작업을 플랜 A/B/C 중 어디로 분류하는가? (한 줄로 명시)
  2. 플랜 A로 분류됐다면, 위임을 시도했는가? 안 했다면 왜?
  3. 마일스톤/사이클처럼 여러 이슈를 묶어 처리할 때도 이슈 단위로 반복 적용
     (하나가 플랜 C라고 나머지도 자동으로 직접 처리하지 말 것)
```

### 2. 위임 비율은 사이클 종료 시 커밋 트레일러로 자동 감사 가능

수동 시간 기록 없이도 `git log`의 `Co-Authored-By` 트레일러 소속만으로 위임 비율을 사후 재구성할 수 있었다. 위임을 시도한 이슈는 위임 CLI의 커밋 attribution을 남기도록 습관화하면, 사이클 종료 후 "계획 대비 실측"을 별도 계측 없이 확인할 수 있다.

### 3. 2차 출처(리서치 요약)도 원본 대조 없이는 채택하지 않는다

리서치 세션이 내린 결론("구조적 문제, 모델 무관")을 그대로 문서화하지 않고 원본 이슈 4건을 직접 열람해 상태·재현 조건을 재확인하니 1건은 일반화가 과했다. 특히 "완료/미계획" 상태와 "어떤 백엔드·모델 조합에 한정된 보고인지"는 제목만으로 알 수 없었다. 리서치 요약에 등장하는 근거 링크는 **결론을 인용하기 전에 최소 상태값(완료/미계획/닫힘 사유)까지는 직접 확인**하는 것을 권장한다.

### 4. 대안 도구 검증 실험 자체의 방법론도 검증하라

이 실험에서 가장 값진 발견은 도구 비교 결과가 아니라 **1차 결과가 내 테스트 하네스의 버그였다**는 것이었다. "재현 안 됨/실패함"이라는 관측이 나오면, 결론을 내리기 전에 "이게 도구의 결함인지, 내 실험 절차의 결함인지"부터 분리해서 확인할 것.
