# 지시문이 산출물로 새는 패턴

위임 명세에 적은 지시가 산출물 안에 그대로 남는 일이 반복된다. 코드를 맡기면 주석 자리에 남고, 문서를 맡기면 본문 문장으로 남는다. **매체만 바뀌고 같은 사고가 반복된다.**

내용이 틀린 것도 아니라서 검수에서 놓치기 쉽다. 읽는 사람 입장에서 맥락 없는 문장이 하나 끼어 있을 뿐이다.

---

## 어떤 모양으로 새는가

### 코드에 맡겼을 때

명세에 "이 함수를 재사용하라" 라고 적으면 산출물 주석에 그 문장이 그대로 붙어 나온다.

```js
// 이 함수를 재사용하라
const result = existingHelper(input);
```

주석은 코드 동작에 영향이 없어서 테스트도 리뷰도 통과한다. 나중에 읽는 사람은 그것이 누구에게 하는 말인지 알 수 없다.

### 문서에 맡겼을 때

문서에서는 **서술문으로 옷을 갈아입고** 들어온다. 명세에 이렇게 적었다.

```
'테스트 코드에 버그를 도입한다' 고 쓰지 마라. 방향이 반대다.
```

산출물에는 이렇게 나왔다.

```
'테스트 코드에 버그를 도입한다'고 쓰는 것은 방향이 잘못된 것으로,
프로덕션 코드의 오류를 직접 유도해 검증해야 한다.
```

문장 자체는 맞는 말이다. 문제는 **아무도 그렇게 쓰자고 하지 않았는데 그것을 반박하고 있다**는 것이다. 독자는 이 문서가 왜 갑자기 그 표현을 변호하는지 알 수 없다.

---

## 왜 생기는가

"X 라고 쓰지 마라" 를 적으려면 **명세 안에 X 를 적어야 한다.**

모델에게는 그 X 도 맥락의 일부다. 금지 대상을 명세에 실어 나른 셈이고, 무엇을 쓰지 말라고 강조할수록 그 표현이 산출물 근처에 남을 확률이 올라간다.

반려를 반복하면 이 효과가 누적된다. 반려 사유에도 그 표현을 다시 적게 되기 때문이다.

---

## 대응 1. 명세를 긍정 서술로만 쓴다

무엇을 쓸지만 적고 무엇을 쓰지 말지는 적지 않는다. **고치고 싶은 표현이 있으면 올바른 표현을 그 자리에 놓는다.**

같은 지점을 두 방식으로 적어 보면 차이가 분명하다.

```
# 부정형 — 금지 대상이 명세에 들어간다
프로덕션에서 반드시 오류가 난다고 쓰지 마라. 오류가 안 날 수도 있다.

# 긍정형 — 쓸 문장만 들어간다
프로덕션에서 오류가 나지 않을 수도 있다. 문제는 검증이 일어나지 않았다는 것이다.
```

실측으로 확인했다. 부정문을 전부 걷어낸 명세로 다시 돌렸을 때 누출이 사라졌다.

```
'쓰지 마라'        0건
'쓰는 것은 방향이'  0건
'주의:'            0건
'금지한다'         0건
```

이어서 다른 문서를 같은 방식(부정문 없이 긍정 서술만)으로 맡겼고, 그 산출물에서도 누출이 없었다. 표본 둘로 규칙이 증명되지는 않지만 적어도 같은 조건에서 재발하지 않았다.

---

## 대응 2. 오염된 스레드를 이어가지 않는다

두 번 반려된 스레드는 **반려 사유와 이전 초안을 맥락으로 들고 있다.** 세 번째 시도도 그 위에서 나온다. 그 맥락에는 지우라고 말한 표현이 전부 들어 있다.

세 번째 반려 대신, 지적사항을 압축해 명세를 새로 쓰고 **새 스레드로 시작하는 편이 싸다.**

실제 회차별 소요다.

| 회차 | 소요 | 결과 |
|---:|---:|---|
| 1판 | 327초 | 사실 오류 3건 |
| 반려 | 1초 | 기록만 남고 재작성 없음 |
| 2판 | 420초 | 지적 3건 반영, **지시문 누출 발생** |
| 새 스레드 | 204초 | 누출 0건, 사실 오류 1건 부분 재발 |

세 번째 반려에 들었을 시간보다 새 호출 204초가 짧았다. 리셋은 손해가 아니다.

**리셋이 만능은 아니다.** 새 스레드에서도 1판에서 지적했던 서술 하나가 부분적으로 되살아났다. 주된 목적(누출 제거)은 달성했고 나머지 한 문장은 승인 후 직접 고쳤다 — 전체 재작성보다 그 편이 정확하고 빨랐다.

### 반려가 재작성을 부르는지 먼저 확인한다

승인 체인에 반려 사유를 실어 재개했더니 **1초 만에 끝났다.** 모델 호출이 없었다.

```
"approved": false,
"rejected_reason": "...",
"log": ["dispatch -> ...", "... 완료", "사람 검수: 반려 (...)", "완료"]
```

반려 경로가 결정만 기록하고 종료하는 구조였다. 문서는 초안 그대로였다. **반려하면 알아서 다시 써 줄 것이라고 가정하지 않는다** — 도구마다 다르므로 한 번 확인해 두면 회차 계획이 달라진다.

---

## 대응 3. 산출물 검사는 존재 확인부터 한다

새 호출 전에 "백지에서 쓰게 한다" 며 대상 파일을 미리 지웠다. 그런데 위임 에이전트는 파일을 만들지 않고 **본문을 체인 페이로드로만 돌려줬다.** 앞선 회차는 기존 파일이 있어서 덮어쓰고 있었던 것이다.

그 상태에서 누출 검사를 돌렸더니 이렇게 나왔다.

```
'쓰지 마라': 0건
'쓰는 것은 방향이': 0건
'고 쓰지': 0건
```

깨끗해 보인다. **파일이 없었다.**

```sh
grep -c "$w" "$F" 2>/dev/null || echo 0
```

`grep` 이 파일을 못 찾아 실패하면 `|| echo 0` 이 0 을 찍는다. 그 0 은 문제가 없다는 뜻이 아니라 **검사가 돌지 않았다**는 뜻이다.

대응은 한 줄이다.

```sh
test -f "$F" || { echo "파일 없음 - 검사 중단"; exit 1; }
```

같은 성질의 실수를 코드 테스트에서 여러 번 겪고도 셸 스크립트에서 그대로 반복했다. **도구가 바뀌면 같은 실수를 새로 배운다**고 보는 편이 안전하다.

---

## 승인이 산출물에 실제로 반영됐는지 확인한다

승인 처리 뒤 체인은 이렇게 보고했다.

```
"approved": true,
"log": ["... 완료", "사람 검수: 승인", "완료"]
```

종료 코드도 0 이었다. 그런데 파일은 그대로였다.

```
---
status: draft
---
```

도구 코드를 보니 치환 대상이 체인이 들고 있는 요약 문자열이었다.

```python
if text == "approve":
    output = state.get("output", "")
    output = output.replace("status: draft", "status: reviewed")
```

산출물이 페이로드로만 오던 시절에는 맞는 코드였고, 에이전트가 **파일을 쓰기 시작하면서 어긋났다.** 체인은 승인이라고 기록하는데 파일은 초안이라고 말하는 상태가 된다.

**성공 출력 문구를 그대로 믿지 않고 다시 조회한 덕에 걸렸다.** 상태를 바꾸는 호출은 결과를 재조회해서 확인한다.

---

## 체크리스트

- [ ] 명세에 "~라고 쓰지 마라" 형태의 문장이 있는가 (있다면 올바른 표현으로 바꿔 쓴다)
- [ ] 산출물에 명세의 표현이 그대로 들어와 있는가
- [ ] 두 번 반려했다면, 세 번째 반려 대신 새 스레드로 다시 시작할 수 있는가
- [ ] 반려가 재작성을 부르는 도구인지 확인했는가
- [ ] 검사를 돌리기 전에 대상 파일이 실재하는지 확인했는가
- [ ] 승인·저장 같은 상태 변경 뒤에 실제 대상을 다시 조회했는가
