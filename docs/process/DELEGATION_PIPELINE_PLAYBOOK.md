## 이 문서의 목적

`DELEGATION_RELIABILITY_CASE_STUDY.md`는 위임 산출물의 **신뢰도가 무너진** 사례를 기록했다. 결론은 "신뢰할 수 있는 부분과 없는 부분이 명확히 구분됐다"였고, 실무 지침은 "재시도는 2회까지, 그 뒤엔 직접 수행"이었다.

이 문서는 그 뒤에 수행한 15건 규모의 UI 개편 사이클(특정 프로젝트명은 밝히지 않는다)에서 **같은 등급의 로컬 모델로 반대 결과를 낸** 기록이다. 143회 위임, 누적 가동 3시간 30분, 직접 코드 개입 1회. 후반부 이슈들은 1차 통과율 100%였다.

달라진 것은 모델이 아니다. **파이프라인이다.** 이 문서는 그 파이프라인을 재사용 가능한 형태로 남긴다.

## 무엇이 달라졌는가

이전 사례의 실패 패턴은 네 가지였다 — 탐색 범위 누락, 사실은 맞는데 판단이 틀림, 검증 결과 조작, 명시적 지시 우회. 이 중 셋은 **모델에게 판단을 시켰기 때문에** 생긴다.

이번 사이클의 전제는 하나다.

> 판단은 프롬프트를 쓰는 단계에서 끝낸다. 모델에게는 전사(轉寫)만 시킨다.

가장 위험했던 작업(색 팔레트 전면 교체)에서 재시도가 0회였던 이유가 이것이다. 44개 값을 전부 계산으로 확정해 프롬프트에 리터럴로 박아뒀다. "어울리는 값을 골라라"라고 시켰다면 판정 자체가 불가능한 산출물이 나왔을 것이다.

이 전제를 지키면 위임의 실패 모드가 바뀐다. 모델이 틀리는 게 아니라 **지시가 틀린 것이 드러난다.** 그것이 이 사이클의 핵심 관측이다.

## 핵심 원칙 여섯 가지

### 1. 판단을 프롬프트 단계에서 끝낸다

선택지가 열려 있는 지시("적절한 값을 골라라", "방향을 정해라")는 위임하지 않는다. 값·문구·구조를 먼저 확정하고, 그것을 옮겨 적는 작업만 넘긴다.

판단이 남아 있는지 알아보는 방법: **산출물을 기계적으로 판정할 수 있는가.** 판정 기준을 쓸 수 없다면 판단이 아직 안 끝난 것이다.

### 2. 단일 출처에서 프롬프트와 검증 기준을 함께 생성한다

프롬프트와 하네스를 따로 관리하면 어긋난다. 실제로 어긋났고, 잔여 개수 0·빌드 통과·테스트 통과 상태에서 40곳이 잘못 치환돼 있었다. 바이트 비교로만 잡혔다.

이후로는 매핑 테이블을 하나 두고 **프롬프트와 검증 기준을 거기서 함께 뽑는다.** 생성 직후 매핑이 실제 코드와 맞는지부터 대조해 위임 전에 지시 오류를 거른다.

### 3. 실행됐음을 종료코드가 아니라 산출물 변화로 확인한다

두 번 크게 물렸다.

- 셸의 단어분할이 동작하지 않아 여러 위임이 **실행조차 되지 않은 채** 종료코드만 남았다. 같은 버그를 사이클 안에서 두 번 반복했다.
- 편집 도구가 파싱할 블록을 찾지 못해 **빈 파일을 남기고 정상 종료**했다. 실패 신호가 전혀 없었다.

대책은 단순하다. 매 실행마다 대상 파일의 해시를 앞뒤로 비교하고, 안 바뀌었으면 그 자리에서 멈춘다.

### 4. 금지 목록이 아니라 허용 형태로 검사한다

어떤 함수에 문자열을 넘기면 판정이 항상 거짓이 되어 분기가 조용히 바뀌는 결함이 있었다. 처음엔 "인자 이름이 특정 단어면 실패"로 검사를 짰다. 같은 성격의 다른 표현을 심은 뮤테이션이 **그대로 통과**했다.

금지 목록은 새 표현이 생길 때마다 뚫린다. 뒤집어서 **허용하는 형태만 통과**시키면(예: 인자는 단순 식별자여야 한다) 표현이 늘어나도 방어가 유지된다.

### 5. 지시문과 산출물을 물리적으로 분리한다

문서를 만드는 위임에서 프롬프트의 지시 문장이 결과물 본문에 그대로 섞였다. 명령형 어미를 선언형으로 바꿨더니 **더 심해졌다** — 지시문이 본문처럼 보이게 됐기 때문이다.

문체를 다듬는 방향은 틀렸다. 지시 줄에 결과물에 절대 나올 수 없는 접두어(`@@` 등)를 붙이고, "결과에 이 접두어가 남으면 실패"로 규정한다. 이러면 **하네스가 판정할 수 있는 규칙**이 된다. "지시문을 옮기지 마라"라는 문장과 결정적으로 다른 점이다.

### 6. 도구 구조 제약은 프롬프트로 우회되지 않는다

두 번 겪었고 둘 다 프롬프트를 아무리 고쳐도 재현됐다.

- 파일 전체를 코드펜스로 감싸 출력하는 편집 형식에서, 내용 자체가 마크다운 문서면 모델이 그걸 답변으로 뱉고 펜스를 붙이지 않는다.
- 같은 형식에서 내용에 중첩 코드펜스가 있으면 파서가 깨진다.

해결은 파이프라인 형태를 바꾸는 것이다. **자리표시자 한 줄을 먼저 파일에 심고, 차분(diff) 형식의 치환으로 교체한다.** 차분 형식이 새 파일을 만들지 못한다는 제약은 시드 파일로 우회되고, 구조 강제라는 이점만 남는다. 긴 문서 위임의 기본 패턴으로 삼는다.

## 하네스 작성 체크리스트

산출물 검증 스크립트를 쓸 때마다 확인한다. 각 항목은 실제로 오판을 냈던 사례에서 나왔다.

1. 앵커(검색 패턴)는 실제 파일에서 **지금 확인한 것**만 쓴다. 추측 금지.
2. "존재 확인"보다 **"개수 대조"**가 형태 변화에 강하다.
3. 소스 형태로 빌드 산출물을 추측하지 않는다. 압축·복사 과정에서 형태가 바뀐다.
4. 정규식 단어 경계는 따옴표·괄호 뒤에서 걸리지 않는다.
5. 문자열 슬라이스 길이는 세어보고 쓴다.
6. **"언급"과 "사용"을 구분한다.** 주석 안의 단어가 매치되면 오탐이다.
7. 개발 경로에서만 검증하면 **운영 경로의 헤더/미들웨어 스택**을 통째로 건너뛴다.
8. 문서 하네스는 형식이 아니라 **주장이 코드와 맞는지**를 본다. 문서는 실행할 수 없으므로 주장 대조가 유일한 실행 검증이다.
9. 금지 목록이 아니라 **허용 형태**로 검사한다(원칙 4).
10. 검사 범위를 좁게 잡으면 **그 밖은 검사한 적이 없는데도 통과로 보인다.** 하한 개수만 단언하지 말고 **각 구간이 실제로 표본에 들어왔는지**를 따로 확인한다.

체크리스트를 하네스 머리에 주석으로 적어두는 것만으로는 지켜지지 않았다. 실제로 적어놓고 어긴 적이 여러 번이다. **게이트를 한 줄 쓸 때마다 "이 앵커가 실제 파일에 지금 있는지 확인했나"를 묻는 편**이 낫다.

## 정량 지표

| 항목 | 값 |
|---|---|
| 위임 실행 횟수 | 143회 |
| 누적 가동 시간 | 3시간 30분 (평균 88초) |
| 오케스트레이터 직접 코드 개입 | 1회 |
| 초기 이슈 1차 통과율 | 1/8 |
| 후반 이슈 1차 통과율 | 4/4, 5/5 (100%) |
| 최장 단일 실행 | 26분 (폭주, 강제 종료) |

폭주 실행은 체감이 아니라 **지표로 진단**했다. 프로세스 경과시간·CPU 상태·산출물 줄 수를 앞선 실행과 비교해 이상을 확인하고 종료했다. 같은 작업의 앞선 회차가 1,400줄을 냈는데 7,700줄을 내고 있었다.

## 실패 책임이 지시하는 쪽으로 옮겨간다

이 사이클에서 관측된 결함을 원인별로 분류하면 이렇다.

| 분류 | 건수 |
|---|---|
| 하네스 결함(검증 스크립트가 틀림) | 15 — 이 중 거짓양성 11 |
| 오케스트레이터 스펙 결함(지시가 틀림) | 4 |
| 도구 구조 제약 | 2 |
| 러너 호출 실수 | 2 |

**모델 산출물 결함은 초기 한 이슈에 집중돼 있고, 그 이후로는 거의 사라진다.** 남는 것은 전부 지시하는 쪽의 결함이다.

이건 좋은 신호이면서 동시에 함정이다. 모델이 지시에 충실할수록 **지시의 결함이 그대로 산출물의 결함이 된다.** 스펙에 "부분 문자열이 나오면 실패시켜라"라고 쓰면 그대로 구현되고, 정작 그 부분 문자열이 대상 파일 주석에 있어서 오탐을 낸다. 호출 지점을 하나 빠뜨리고 넘기면 그 자리에 잘못된 인자가 들어가 분기가 조용히 뒤집힌다.

그래서 실무적으로는 이렇게 뒤집힌다.

> 게이트가 실패를 뱉으면 **대상 코드보다 게이트를 먼저 의심한다.**

이 사이클에서 그쪽이 맞은 비율이 높았다(15건 중 11건). 다만 이건 파이프라인이 성숙한 뒤의 이야기다. 초기에는 반대였다.

## 재시도 정책 갱신

기존 지침은 "동일 산출물에 대한 재시도는 2회까지, 3회차부터는 직접 수행"이었다. 이번 사이클의 관측으로 조건을 나눈다.

```
재시도 전에 원인을 분류한다:

  산출물이 지시와 다름 (누락·오타·범위 초과)
    → 빠뜨린 부분을 리터럴로 명시해 재위임. 횟수 제한 없음.
      이 유형은 3~4회차에도 통과율이 높았다.

  같은 실패가 프롬프트를 고쳐도 반복됨
    → 도구 구조 제약을 의심한다. 프롬프트가 아니라 파이프라인 형태를 바꾼다.
      (편집 형식 교체, 시드 파일 도입, 파일 단위 분할)

  지시 자체가 틀렸음이 드러남
    → 재위임 전에 지시를 고친다. 모델은 잘못이 없다.
      이 경우를 "위임 실패"로 집계하면 통계가 왜곡된다.

  위임 도구가 거부함 (권한·무시목록 등)
    → 거부 사유를 먼저 읽는다. 실패가 아니라 환경 문제일 수 있다.
      실제로 한 번은 도구의 거부가 설정 오류를 알려줬다.
```

한 파일에 여러 편집이 필요하면 **파일당 하나씩 나눈다.** 두 파일 네 편집을 한 프롬프트에 넣었더니 한 편집만 적용하고 멈춘 사례가 있다.

## 2차 사이클에서 추가된 것

시각 개편 성격의 사이클(웹 프런트엔드, Node/Express/SQLite 앱)을 한 번 더 돌리며 얻은 것들이다.

### 7. 큰 파일의 국소 편집은 무관한 블록을 함께 지운다

1000행이 넘는 파일에 "여기 한 곳만 고쳐라" 를 시켰더니 지시와 무관한 섹션 40여 줄을 통째로 삭제했다. **두 파일에서 각각 한 번씩, 같은 형태로 반복됐다.** 프롬프트에 "다른 곳을 건드리지 마라" 를 리터럴로 적어둔 상태였는데도 그랬다.

프롬프트로 막히지 않는다고 본다. 대책은 파이프라인 쪽이다.

```
큰 파일에 국소 편집을 위임할 때:

  a. 산출물을 그대로 받지 않는다. 지시한 추가분만 골라내 base 에 다시 얹는다.
     삭제 헝크는 기본적으로 버린다 — 지시에 삭제가 없었다면 그것은 산출물이 아니다.

  b. 통합 전에 "지시하지 않은 삭제가 있는가" 를 기계로 확인한다.
     git diff 의 삭제 줄 수가 예상 범위를 넘으면 멈춘다.

  c. 가능하면 편집 대상을 새 파일로 뺀다. 신규 파일 작성은 같은 문제가 없었다.
```

a 는 "모델 산출물을 사람이 고치는 것" 과 다르다. **범위 안의 것을 선별하는 통합 작업**이며, 새로 쓰는 코드가 없다. 재위임 정책과 충돌하지 않는다.

### 8. 검증 환경이 오염되면 없는 결함을 만들어낸다

브라우저 자동화로 시각 검증을 하다 "특정 컨테이너가 폭 0 으로 마운트되고 복구되지 않는다" 는 결함을 발견했다고 판단하고 이슈까지 열었다. 나중에 확인해 보니 **브라우저 패널이 숨겨진 상태**였다.

```
document.visibilityState  →  'hidden'
window.innerWidth         →  0
window.innerHeight        →  0
```

뷰포트가 0×0 이면 폭 0 을 재는 것이 정상 동작이다. 반응형 분기도 전부 깨져서, 데스크톱 전용 요소가 `display: none` 으로 잡혔다.

이 잘못된 진단을 근거로 구조를 바꿨다면 **있지도 않은 문제를 고치는** 셈이 된다. 이슈에 정정을 남기고 재확인 대상으로 돌렸다.

대책은 단순하다. **시각 검증을 시작하기 전에 뷰포트가 유효한지 먼저 잰다.**

```
검증 전 사전 확인:
  document.visibilityState === 'visible'
  window.innerWidth  > 0
  window.innerHeight > 0
셋 중 하나라도 어긋나면 그 회차의 시각 관측은 증거로 쓰지 않는다.
```

### 9. 테스트 하네스가 조용히 아무것도 검증하지 않을 수 있다

차트 렌더를 확인하는 테스트를 붙이려다, 기존 셋업의 관찰자 스텁이 **관찰만 받고 콜백을 부르지 않는다**는 것을 발견했다. 컨테이너가 크기를 영영 못 배우므로 차트가 든 화면은 테스트에서 늘 빈 채로 통과하고 있었다.

스텁을 고쳐 크기를 통보하게 했더니 컨테이너까지는 만들어졌지만 **도형은 여전히 비어 있었고, 여러 차트 유형이 모두 같았다.** 즉 그 환경에서는 차트 렌더를 검증할 수 없다.

여기서 중요한 건 스텁을 고친 것이 아니라 **"이 하네스로는 검증할 수 없다"를 문서에 남긴 것**이다. 남기지 않으면 다음 사람이 같은 자리에서 같은 시간을 쓴다.

```
빈 스텁을 둘 때는 그것이 무엇을 검증하지 못하게 만드는지 함께 적는다.
"없어서 넣어둔 것" 과 "동작을 흉내 내는 것" 은 다르다.
```

### 10. 스택 PR 은 깊은 것부터 머지해야 한다

의존관계가 있는 PR 을 쌓아 올린 뒤 얕은 것(공통 base)을 먼저 머지했다. 그 base 브랜치가 소진된 뒤에 깊은 PR 두 개가 머지됐고, 커밋은 **아무 데로도 흘러가지 않는 브랜치에만 남았다.**

플랫폼은 두 PR 을 `MERGED` 로 표시한다. 실제로 머지되긴 했기 때문이다 — 대상이 통합 브랜치가 아니었을 뿐이다. **상태만 보면 정상으로 보여서 놓치기 쉽다.**

발견은 테스트 수로 했다. 머지 후 통합 브랜치가 294 건이었는데 두 모듈이 들어갔으면 326 이어야 했다.

```
스택 PR 규칙:
  - 깊은 것(base 가 다른 feature 브랜치인 것)부터 머지한다.
  - 얕은 것을 먼저 머지해야 한다면, 머지 직후 그 브랜치를 삭제해
    플랫폼이 남은 PR 의 base 를 자동 재지정하게 한다.
  - 머지 후 통합 브랜치에서 테스트 수를 확인한다. 파일 존재 확인보다 빠르고 확실하다.

애초에 스택을 만들지 않는 편이 낫다. 파일이 겹치지 않으면 전부 통합 브랜치 기준으로 낸다.
```

### 11. 명령이 성공을 보고해도 산출물은 안 바뀔 수 있다 (원칙 3의 확장)

원칙 3 은 위임 실행에 대한 것이었는데, 같은 형태를 **플랫폼 API 호출**에서 다시 만났다.

- CLI 가 성공처럼 보이는 출력(대상 URL)을 내놓았지만 실제 상태는 바뀌지 않았다. 직접 조회하니 서버가 `422` 로 거부하고 있었다.
- 셸 변수에 담은 여러 플래그가 단일 인자로 묶여 명령이 **실행조차 되지 않았다.** 1차 사이클에서 두 번 반복된 그 버그가 다른 도구에서 또 나왔다.

**종료코드와 출력 문구를 신뢰하지 않는다.** 상태를 바꾸는 호출은 바꾼 뒤 다시 조회해서 확인한다.
