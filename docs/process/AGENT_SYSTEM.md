# 에이전트 시스템 가이드

## 에이전트 조직도
```
Claude Code (Main Orchestrator)
└── Sub-agents (Search/Research, Code Review, etc.)
    └── VANCE (Local lightweight tasks)
        └── ORACLE (Heavy analysis, limited use)
```

## 각 계층의 역할과 사용 기준
- **Claude Code (메인 오케스트레이터)**  
  - 직접 처리: 단순한 코딩 작업, 직관적 판단이 필요한 경우  
  - 위임 기준: 서브에이전트/하위 작업이 필요하지 않은 경우 (예: 파일 생성, 간단한 테스트 코드 작성)

- **서브에이전트 (탐색/리서치, 코드리뷰 등)**  
  - 위임 기준: 도메인 전문성 필요 (예: 외부 API 문서 분석, 코드 리뷰)  
  - VANCE 대체 가능 여부 확인 후 호출 (예: "문서 초안 작성"은 VANCE로, "복합적 분석"은 서브에이전트로)

- **VANCE (로컬 경량 위임 작업)**  
  - 위임 기준: 반복적/가벼운 작업 (예: 문서 초안 작성, 간단한 데이터 정리)  
  - **제외 사항**: 복잡한 판단, 검증이 필요한 작업 (예: "이 코드가 보안 취약점이 있는지 분석" → ORACLE)

- **ORACLE (무거운 분석/검증)**  
  - 위임 기준: **절대적 제한**  
    - 복잡한 시스템 설계 검증 (예: "이 아키텍처가 확장성 문제 없을까?")  
    - **사전 점검 필수**: VANCE/서브에이전트로 해결 가능한지 확인 후 사용  
    - **사용 금지 사례**: 단순한 문장 수정, 반복적 데이터 변환

## ORACLE 호출 규칙
- **병렬 호출 금지**: 모든 ORACLE 호출은 **순차적 실행**으로 제한  
  - *사고 사례*: 과거 ORACLE을 동시에 여러 번 병렬 호출했다가 메모리 부족(OOM) 및 처리 지연/블로킹이 발생한 적이 있어, 이 규칙이 제정되었습니다.
- **리소스 확인 필수**:  
  - 호출 전 시스템/GPU 메모리 여유 확인 (`free -h`, `nvidia-smi` 등 환경에 맞는 도구 사용)
- **사용 후 정리**: ORACLE 호출 결과를 저장한 뒤, 불필요하게 프로세스를 띄워두지 않기

## 세션 위생
- **중복 세션 방지**:  
  - 새 Claude Code 세션을 시작하기 전, 동일 작업에 대해 이미 실행 중인 세션이 없는지 먼저 확인
  - "Claude Code 세션 중복 생성" 사고(2026년 7월)로 인해 **반드시 확인** 필요
- **세션 정리**:  
  - 작업 종료 후 더 이상 필요 없는 세션은 정리하여 리소스 낭비 방지

## 스케줄러 세션 제약사항 (2026-07-23 확인)

스케줄러 세션에서는 `mcp__dispatch__*` 도구(start_code_task, send_message 등)가 로드되지 않는다.
플랫폼 인프라 버그 (anthropics/claude-code#43397).

**워크어라운드**: 스케줄 태스크 프롬프트 첫 줄을 다음과 같이 작성:
> "직접 작업하지 말고 서브에이전트를 사용해서 전체 작업을 처리하라."

서브에이전트는 MCP 도구가 정상 초기화된다.

**대안**: bash로 파일 플래그 작성 후 외부 cron/launchd로 트리거.

## Claude:opencode 작업 분배 비율 플랜 (2026-07-24 추가)

opencode(로컬 LLM)와 Claude를 작업 성격에 따라 적절히 혼합해서 사용. Claude를 아예 안 쓰거나 전부 쓰는 것이 아닌, **작업 유형별 비율 설정**이 핵심.

### 플랜 A — 1:9 (Claude 최소, opencode 주도)

**적용 상황:**
- 스펙이 명확한 반복 구현 (CRUD 엔드포인트, UI 컴포넌트, 스타일 수정)
- 테스트 코드 작성, 보일러플레이트 생성
- 포맷팅, 리팩토링, 파일 정리

**Claude 역할 (10%):** 프롬프트 작성 + 결과물 최종 검토만  
**opencode 역할 (90%):** 실제 코딩 전담, PR 초안 작성까지

---

### 플랜 B — 3:7 (Claude 조율, opencode 실행) — 기본값

**적용 상황:**
- 일반적인 기능 이슈 진행
- 디버깅 (원인 분석은 Claude, 수정 실행은 opencode)
- 기존 코드베이스 위에 새 기능 추가

**Claude 역할 (30%):** 이슈 분석, 설계 방향 결정, 예외/판단 지점 개입, PR 리뷰  
**opencode 역할 (70%):** 구현 실행, 테스트 실행, 커밋

---

### 플랜 C — 5:5 (균형)

**적용 상황:**
- 아키텍처 결정이 포함된 구현
- 보안·성능 민감 코드
- 새로운 기술 스택 도입, 설계 트레이드오프 판단 필요
- 복잡한 버그 (멀티 레이어 원인 분석)

**Claude 역할 (50%):** 설계 검토, 보안 리뷰, 구현 방향 적극 개입  
**opencode 역할 (50%):** Claude 지시 따라 구현 실행

---

### 비율 결정 흐름

```
이슈 시작 시:
  스펙이 완전히 명확? → 1:9 (플랜 A)
  일반 기능 이슈?     → 3:7 (플랜 B, 기본값)
  보안/아키텍처 포함? → 5:5 (플랜 C)
  사용자가 예외 발동?  → 예외 규칙 섹션 참조
```

**기본값은 3:7 (플랜 B)**. 불명확하면 플랜 B로 시작하고 작업 중 조정.

### 위임 게이트 체크리스트 (필수, 스킵 불가) — 2026-07-26 추가

이 흐름표가 문서로 존재하는 것과, 매 이슈 착수 시 실제로 참조되는 것은 다르다. 한 감사대응 사이클(24개 이슈)에서 이 표를 단 한 번도 참조하지 않은 채 전량 직접 처리(위임 비율 100:0)로 끝난 사례가 확인됐다 — 위임이 실패한 게 아니라 판단 지점 자체가 발동하지 않은 것이다. 자세한 사례: [`DELEGATION_GATE_SKIP_CASE_STUDY.md`](./DELEGATION_GATE_SKIP_CASE_STUDY.md).

재발 방지를 위해 다음을 **이슈/작업 착수 시점의 필수 첫 단계**로 못박는다. 오케스트레이터는 구현에 들어가기 전 아래 세 질문에 답한 뒤 진행해야 한다.

```
트리거 ①  이슈 착수 시 (스킵 불가):
  1. 이 작업, 위임 가능성 체크했나?
     → 아직 안 했으면 여기서 멈추고 먼저 플랜 A/B/C 중 하나로 분류할 것
       (분류 기준은 위 「비율 결정 흐름」 그대로 사용)
  2. 플랜 A/B로 분류됐다면, 위임을 실제로 시도했는가?
     → 시도 안 했다면 그 이유를 한 줄로 남길 것
       (예: "최근 위임 CLI 신뢰도 사고로 이번만 직접 처리" — 근거 없이 그냥
       넘어가지 말 것. 이유 자체가 부실해도 최소한 "왜 안 했는지"가 기록에
       남아야 사후에 100:0 같은 패턴을 감지할 수 있다)
  3. 마일스톤/사이클처럼 여러 이슈를 묶어 처리할 때도 이슈 단위로 반복 적용할 것
     (하나가 플랜 C라고 나머지도 자동으로 직접 처리하지 말 것 — 다수의 플랜
     B/C 작업 흐름에 소수의 플랜 A 대상 작업이 묻혀 식별 안 되는 게 실제
     관측된 실패 패턴이다)

트리거 ②  산출물 커밋 직전 (스킵 불가):
  4. 지금 커밋하려는 것 중 문서가 있는가?
     (신규 문서, 또는 기존 문서의 대량 개정 — 오타·링크 수정 같은 소규모
     수정은 해당 없음)
     → 있으면 여기서 멈추고 4-1, 4-2에 답할 것
  4-1. 그 문서 초안을 위임했는가?
     → 안 했다면 왜 안 했는지 한 줄로 남길 것 (2번과 같은 규칙)
  4-2. 프로세스 문서(docs/process/*)라면 process_doc 승인을 받았는가?
     → confirm-chain 게이트가 커밋을 막는다. 막혔다면 그게 정상 동작이다.
       우회(--no-verify)는 승인 기록을 남기지 않으므로 사후 감사에서
       누락으로 잡힌다
```

**왜 트리거 ①만으로는 부족한가.** 트리거 ①은 "이슈 착수"라는 순간이 실제로 존재하는 작업 형태를 전제한다. 그런데 감사 → 분석 → 문서개정처럼 하나의 흐름이 여러 산출물로 이어지는 작업에서는 그 순간이 한 번도 오지 않는다. 실제로 트리거 ①이 도입된 바로 다음 날, 한 연속 작업(문서 4건, 1,500줄 이상)에서 게이트가 단 한 번도 발동하지 않은 채 전량 직접 처리로 끝난 사례가 관측됐다 — 오케스트레이터가 규칙을 어긴 게 아니라, **규칙의 발동 조건 자체가 그 작업 형태에서 성립하지 않았다.** 반면 "커밋한다"는 순간은 산출물이 나오는 모든 작업에 예외 없이 존재하고 외부에서 관찰 가능하다. 그래서 트리거를 하나 더 둔다.

**게이트가 문서로만 존재하면 다음 날 또 안 걸린다.** 트리거 ②의 4-2는 `tools/confirm-chain` 의 커밋 훅으로 실제 강제된다(설치: `tools/confirm-chain/install-hooks.sh`). 4와 4-1은 여전히 사람/오케스트레이터의 자기점검이지만, 4-2가 걸리는 순간 4·4-1도 함께 상기되도록 순서를 배치했다. 이것이 TPS Jidoka(이상 시 자동 정지)를 이 체크리스트에 적용한 지점이다.

**사후 감사 방법**: 위임을 시도한 작업은 위임 CLI의 커밋 attribution(`Co-Authored-By` 등)을 남기는 걸 습관화한다. 사이클 종료 후 `git log`의 co-author 트레일러 소속만 훑어보면, 수동 시간 기록 없이도 "계획한 비율 대비 실측이 어긋났는지"를 객관적으로 재구성할 수 있다.

## 예외 규칙: 기본 운영 룰 일시 해제 (2026-07-24 추가)

### 기본 원칙 (평상시)
- 루틴 코드 실행은 **로컬 LLM(opencode/aider via VANCE)**으로 위임 → Claude 토큰 절약
- Cowork(EVA)는 조율/보고 취합만, Code 세션(AXEL)도 직접 코딩 금지, opencode에 위임

### 예외 발동 조건

사용자가 **아래 중 하나의 신호**를 보낼 때:
- "이건 기존 룰에서 벗어나서 진행해줘"
- "예외 발동", "예외 처리", "이번만 예외"
- 기타 "기존 방식에서 벗어난다"는 뉘앙스가 명확한 경우

### 예외 발동 시 Claude의 행동 규칙

> **바로 진행하지 말고, 먼저 되묻기 필수**

예외 신호 수신 시 반드시 아래 내용을 확인 후 진행:

1. **어떤 룰을 예외 처리할 것인지** (예: "opencode 위임 룰", "단일 세션 룰", "토큰 절약 원칙" 등)
2. **예외의 범위와 기간** (예: "이번 작업만", "오늘 하루", "명시적으로 종료할 때까지")
3. **구체적으로 어떻게 진행할지** (예: "Cowork+Code 병행", "Claude가 직접 코딩", "복수 레포 동시 작업")

사용자 확인 후에만 예외 모드 진입. 추측으로 먼저 실행 금지.

### 예외 종료
- 해당 작업 완료 또는 사용자의 명시적 "종료/원래대로" 발언 시 기본 원칙 복귀
- 예외는 **1회성** — 다음 요청에서 자동 이월 없음
- 다음 대화/세션에서는 기본 원칙이 자동 복원됨

### 예외가 필요한 상황 예시
- 긴급 병행 작업 (다수 레포 동시 진행)
- 로컬 LLM 이슈로 opencode 사용 불가
- 사용자가 작업 속도를 토큰 비용보다 우선시

## 코드 세션의 사용자 확인 방식 (2026-07-25 추가)

**코드 세션(AXEL 등)은 AskUserQuestion 같은 direct-ask UI(전용 질문/선택지 위젯)를 사용하지 않는다.** 사용자 확인이 필요하면 항상 **일반 채팅 텍스트로 질문을 남겨, Dispatch가 채팅으로 릴레이하는 경로**를 통해 전달한다.

- **사고 사례(2026-07-25)**: 한 코드 세션이 AskUserQuestion을 호출했는데, 사용자가 모바일 환경이라 해당 위젯이 렌더링되지 않아 응답이 불가능했고, 세션이 무기한 대기 상태로 멈춰 결국 강제 종료됐다.
- 이는 모바일 호환성을 위한 임시 우회책이 아니라, **User → EVA → AXEL 다층 구조 전체에서 지켜야 할 정식 프로세스**다. direct-ask UI는 그 자리에서 즉시 상호작용 가능한 단일 세션 환경을 전제로 하는데, 이 구조에서는 응답 채널이 항상 Dispatch를 거치는 채팅 텍스트이기 때문이다.
- **적용 범위**: Claude Code(AXEL) 세션 전반. Cowork(EVA)가 사용자와 직접 대화하는 경우는 이 제약 대상이 아니다(이미 실시간 채팅 채널이므로).

## 주의 사항
이 문서는 VinylStage의 **초안 가이드**이며, 프로젝트별 실제 운용 경험에 따라 **사람이 검수/보완해야 합니다**.  
특히 ORACLE 사용 기준과 VANCE/서브에이전트 분배는 프로젝트 별로 다를 수 있으니, 실제 작업 시 반드시 확인해 주세요.
