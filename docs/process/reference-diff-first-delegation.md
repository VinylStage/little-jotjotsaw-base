## 이 문서의 목적

기존 위임 문서들([`DELEGATION_PIPELINE_PLAYBOOK.md`](./DELEGATION_PIPELINE_PLAYBOOK.md) 등)은 테스트 작성·UI 개편처럼 **새로 쓰는** 위임을 다뤘다. 이 문서는 **기존 코드를 고치는** 리팩토링형 위임(중복 헬퍼 통합, 미사용 이름 삭제)에서 관측한 것을 다룬다.

결론을 먼저 적는다. 같은 모델이 "특정 위치를 정확히 고치는" 작업 두 건은 전부 실패했고, "지우기만 하는" 작업 한 건은 성공했다. 실패한 두 건은 위임 **전에** 사람이 만들어 둔 정답 diff 가 그대로 반영됐다. 명세 검증용으로 만든 것이 폴백이 됐다.

## 관측 결과

로컬 모델 qwen3-coder 30B, aider diff 편집 형식. 검증이 실패하면 실패 출력을 되던지는 최대 3라운드.

| 작업 | 성격 | 라운드 | 결과 | 반영된 것 |
|---|---|---|---|---|
| A. 6개 파일에 흩어진 "로컬 오늘 날짜" 재구현·2자리 패딩 함수를 공용 모듈 import 로 교체 | 위치 지정 수정 | 3 (3라운드 중단) | 실패 | 사람의 참조 diff (위임비율 0%) |
| B. 세 화면에 복사된 차트 축 포매터를 공용 모듈로 옮기고 단위 테스트 추가 | 위치 지정 수정 + 삽입 | 3 (3라운드 중단) | 실패 | 사람의 참조 diff (위임비율 0%) |
| C. 5개 파일에서 미사용 이름 삭제 | 순수 삭제 | 2 | 통과 | 모델 산출 +2/−13, 사람 보정 −1 (약 94%) |

## 실패 유형

### 1. 추가 지시를 기존 줄에 병합한다

- **무슨 일**: "이 require 줄 바로 뒤에 새 require 줄을 추가하라" 를 받고, 새 줄을 추가하면서 **기존 require 의 구조분해에도 같은 이름을 끼워 넣었다.** 같은 파일에 같은 상수가 두 번 선언돼 파일 로드 자체가 실패했다(SyntaxError). 세 파일에서 같은 방식으로 났고 테스트 20여 건이 떨어졌다
- **왜 위험한가**: 파일이 로드되지 않으면 그 파일을 쓰는 테스트가 모두 떨어진다. 실패 목록만 보면 넓은 회귀처럼 보여 원인이 한 줄이라는 것이 가려진다
- **대응**: 린트(`no-redeclare`·파싱 에러)를 테스트보다 먼저 돌려 실패 사유를 한 줄로 좁혀 되던진다

### 2. "본문만 바꾸라" 를 "없애라" 로 수행한다

- **무슨 일**: "함수 본문만 한 줄로 바꾸고 이름과 export 는 유지하라" 를 받고 **함수를 통째로 지웠다.** 다른 모듈이 그 이름을 import 하고 있었다
- **왜 위험한가**: 중복을 없애라는 작업 목적과 방향이 같아서, 모델 입장에서는 "더 철저히 한" 편집이다. 명세의 제약(이름 유지)이 목적에 밀린다
- **대응**: 유지해야 하는 이름을 검증 조건으로 만든다(`grep -q 'function 이름'` 등). 명세 문장으로만 두지 않는다

### 3. 수정 라운드가 상태를 악화시킨다

- **무슨 일**: 2라운드에서 실패 출력(중복 선언)을 받고도 중복 선언을 그대로 두었고, 1라운드에서 맞게 넣었던 **다른 파일의 import 를 지웠다.** 린트 에러가 5건으로 늘었다
- **왜 위험한가**: 되던지기 루프는 "라운드마다 나아진다" 를 전제로 한다. 그 전제가 깨지면 마지막 라운드의 산출물이 첫 라운드보다 나쁠 수 있다
- **대응**: 라운드마다 실패 건수를 기록하고 **늘면 즉시 중단**한다. 이 사례의 3라운드는 SEARCH 불일치 재시도만 7회, 10분 42초를 썼다

### 4. 명세에 없는 기존 단언을 바꾼다

- **무슨 일**: B 의 1라운드는 명세 편집이 정답과 거의 같았다. 그런데 명세에 없는 **기존 테스트의 기대값**을 바꿨다(`'1,234,567'` → `'1,2,567'`). 2라운드도 같은 오염을 유지했다
- **왜 위험한가**: 이번에는 틀린 값으로 바꿔서 검증이 떨어졌다. **구현에 맞춰 기대값을 바꿨다면 검증은 통과했다.** 테스트가 검수 기준인 한, 기존 단언의 변경은 검수 기준 자체의 변경이다
- **대응**: 위임 전 기존 `test`/`it` 블록과 단언 줄의 해시를 떠 두고, 명세가 허용한 블록 밖에서 바뀌면 실패로 판정한다

### 5. 재시도 중에 금지 대상으로 번진다

- **무슨 일**: B 의 3라운드는 명세가 "손대지 말라" 고 명시한, **다른 작업 흐름이 소유한 파일**을 고치기 시작했다(8분 시점에 사람이 중단하고 원복). A 의 3라운드도 중단 시점에 편집 목록 밖의 공용 모듈을 고치고 있었다
- **왜 위험한가**: 범위 검사는 라운드가 **끝날 때** 돈다. 라운드 도중에 끊으면 그 오염은 검사되지 않고 트리에 남는다. 이 사례에서는 사람이 diff 를 보고 원복했다
- **대응**: 중단도 라운드 종료와 같은 정리 경로(범위 검사 → 원복)를 타게 한다. 수정 라운드 프롬프트에 원래 명세 전문을 다시 붙이면 명세 속 "손대지 말 파일" 이름이 편집 후보로 읽히는 것으로 보인다(**추정**). 금지 목록은 프롬프트가 아니라 편집 대상 파일 목록에서 빼는 것으로 강제한다

## 참조 diff 선행

세 작업 모두 위임 전에 사람이 정답 diff 를 직접 만들어 테스트를 돌렸다. 목적은 **명세가 성립하는지** 확인하는 것이었다 — 명세대로 고쳐도 테스트가 떨어진다면 모델이 아니라 명세가 틀린 것이다.

| 작업 | 참조 diff 검증 |
|---|---|
| A | 서버 1917 통과 / 0 실패 |
| B | 클라이언트 1795 / 1795 |
| C | 서버 1917 / 0 · 클라이언트 1790 / 1790 |

위임이 실패한 A·B 는 이 diff 를 그대로 반영했다. 위임 실패가 일정 지연으로 번지지 않았다. 대신 위임비율은 0% 로 적는다 — 폴백을 위임 산출로 세면 비율이 거짓이 된다.

비용: 참조 diff 를 만드는 데 드는 시간은 작업을 직접 하는 시간과 거의 같다. 그래서 이 방식은 **위임으로 시간을 버는 수단이 아니라, 위임을 안전하게 시도하는 수단**이다. 위임이 성공하면 사람의 diff 와 모델의 diff 를 대조하는 것으로 검수가 끝난다(C 에서는 빈 줄 2개만 달랐다).

반영 뒤에는 돌연변이로 테스트가 바뀐 줄을 잡는지 쟀다.

- A: 8건 중 7 사살. 처음에는 기본값 날짜 1건이 살아남아 그 줄을 잠그는 테스트를 추가한 뒤 사살. 나머지 1건은 **동치 돌연변이** — 말일 값이 항상 28~31 이라 2자리 패딩이 원래 무동작이었다
- B: 6건 중 5 사살. 1건은 차트 축이 테스트 환경에서 그려지지 않아 관찰 불가
- 새 테스트의 기대값은 검사 대상 헬퍼로 만들지 않고 테스트 안에서 따로 계산했다. 같은 함수로 기대값을 만들면 동어반복이다

## 검증 쪽의 결함

C 의 1라운드와 2라운드는 diff 가 **글자 그대로 같았는데** 1라운드만 검증에 실패했다. 검증 명령이 `grep -q` 로 테스트 출력을 삼켜서 어느 테스트가 왜 떨어졌는지 남지 않았다. 알려진 간헐 실패로 추정하지만 확정할 수 없다.

같은 입력에 다른 판정이 나왔다는 사실은 남았는데, 그것이 모델 탓인지 환경 탓인지 귀속할 수 없게 된 것이다. 위임비율과 실패 원인 통계는 이 귀속에 기대므로, 검증 출력은 판정과 별개로 **항상 파일로 남긴다.**

## 체크리스트

- [ ] 위임 전에 참조 diff 를 만들어 테스트로 명세를 검증했다
- [ ] 편집 대상 파일 목록에 금지 대상이 들어 있지 않다 (프롬프트 문장으로만 금지하지 않는다)
- [ ] 유지해야 하는 이름·export 를 검증 조건으로 적었다
- [ ] 기존 테스트 블록·단언 줄의 변경을 감지한다
- [ ] 삭제 작업이면 "추가된 줄 수 상한" 을 검증 조건에 넣었다
- [ ] 라운드마다 실패 건수를 기록하고, 늘면 중단한다
- [ ] 중단해도 범위 검사·원복이 돈다
- [ ] 검증 명령의 출력을 파일로 남긴다 (`grep -q` 로 삼키지 않는다)
- [ ] 폴백으로 반영한 diff 는 위임비율에 넣지 않는다
