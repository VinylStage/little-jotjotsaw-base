## 이 문서의 목적

여러 AI 에이전트 세션과 로컬 모델 위임을 **동시에** 굴려 하나의 저장소를 개발할 때 지켜야 할 운영 규칙이다. 실제 병행 개발에서 나온 실패에서 규칙을 끌어냈다.

파일 충돌은 워크트리로 막을 수 있다. **막기 어려운 것은 그 바깥**이다 — 실데이터 파일, 포트, 마이그레이션 번호, PR 베이스, 승인 권한. 이 문서는 주로 그쪽을 다룬다.

특정 프로젝트의 구성이나 사건 기록은 담지 않는다. 어느 저장소에서도 그대로 적용할 수 있는 규칙만 쓴다.

---

## 1. 세션 격리

### 1.1 자기 작업은 별도 워크트리에서 한다

**규칙**: 각 세션은 `git worktree` 로 자기 트리를 파서 작업한다. 메인 체크아웃은 비워 둔다.

**근거**: 메인 체크아웃을 한 세션이 점유하면, 다른 세션이나 사람이 거기서 브랜치를 바꾸는 순간 점유한 세션의 작업 트리가 통째로 옮겨진다. 커밋하지 않은 변경이 있으면 그대로 위험해진다.

**실행**: 통합 브랜치를 기점으로 트리를 만든다.

    git worktree add -b <브랜치> ../<저장소>-<주제>-wt origin/<통합브랜치>

작업이 끝나면 트리를 정리한다. 메인 체크아웃은 어느 세션도 소유하지 않는 중립 상태로 둔다.

### 1.2 의존성 디렉터리 심링크의 함정

워크트리마다 의존성을 새로 설치하면 디스크와 시간이 든다. 메인 체크아웃의 디렉터리를 심링크로 거는 방법을 쓸 수 있는데, 여기에 함정이 있다.

**`.gitignore` 의 `node_modules/` 처럼 뒤에 슬래시가 붙은 패턴은 디렉터리만 무시한다. 심링크는 무시되지 않아 추적되지 않은 파일로 뜬다.**

**실행**: 스테이징할 때 `git add -A` 를 쓰지 않고 **항상 경로를 명시한다.** 심링크가 커밋에 섞여 들어가면 다른 환경에서 깨진 경로를 참조하게 된다.

## 2. 공유 자원

워크트리는 **파일만** 나눈다. 아래는 여전히 공유된다.

### 2.1 실데이터 파일

**규칙**: 미리보기·수동 확인용 서버는 실데이터가 아니라 **백업 사본**을 물린다. 데이터 경로는 환경변수로 주입한다.

**근거**: 조회 전용으로 보이는 경로에도 쓰기가 숨어 있을 수 있다. 조회 시점에 상태를 자가 교정하는 구현이 대표적이다. 서버를 실데이터에 붙이는 순간 그 쓰기가 실데이터에 남는다.

파일 잠금 문제도 있다. 여러 프로세스가 같은 파일을 열면 저널·체크포인트 동작이 서로 간섭한다.

**실행**: 백업에서 사본을 떠 임시 경로에 두고, 서버 실행 시 데이터 경로 환경변수로 그 사본을 지정한다. 실행 중 실데이터를 연 프로세스가 없는지 `lsof` 로 확인한다.

### 2.2 포트

**규칙**: 세션마다 포트를 다르게 배정한다. 기본 포트는 아무도 쓰지 않는다.

**근거**: 기본 포트에 두 세션이 동시에 뜨면 하나는 기동에 실패하거나, 더 나쁘게는 **먼저 뜬 쪽에 붙어 남의 환경을 조작한다.**

**실행**: 실행 설정 파일에 세션별 항목을 만들고 포트를 명시한다. 포트 고정 옵션(`--strictPort` 등)을 켜 조용히 다른 포트로 넘어가지 않게 한다.

### 2.3 프록시 대상 — 포트만 나누면 소용없다

**규칙**: 프런트엔드 개발 서버의 API 프록시 대상도 환경변수로 열어 둔다.

**근거**: 프록시 대상이 기본 포트로 하드코딩돼 있으면, **서버 포트를 나눠도 화면은 여전히 기본 포트를 본다.** 거기에 다른 세션의 서버가 떠 있으면 내 화면이 그 세션의 데이터를 읽고 쓴다. 포트 분리가 성립하지 않는다.

**실행**: 프록시 설정을 `환경변수 || 기존 기본값` 형태로 바꾼다. 기본값을 유지하면 단일 세션 개발 흐름은 바뀌지 않는다.

**검증**: 분리했다고 믿지 말고 확인한다. 기본 포트를 비운 상태에서 화면이 정상 동작하면 새 경로로 붙은 것이다.

### 2.4 마이그레이션 번호

**규칙**: 순번을 쓰는 자원(스키마 마이그레이션 등)은 **파일을 만들기 직전에** 다른 세션의 브랜치까지 훑어 선점 여부를 확인한다.

**근거**: 통합 브랜치만 보면 아직 머지되지 않은 다른 세션의 브랜치가 잡은 번호를 못 본다. 두 세션이 같은 번호를 쓰면, 러너가 파일명을 키로 삼는 경우 양쪽 다 적용되긴 하지만 **적용 순서가 사전순에 좌우되고 순번의 의미가 깨진다.**

**실행**: 원격 브랜치 전체에서 해당 디렉터리를 확인한다.

    for b in $(git branch -r | grep -v HEAD); do
      git ls-tree --name-only "$b" migrations/ 2>/dev/null
    done

충돌을 발견하면 **브랜치 수가 적은 쪽이 옮긴다.** 스택으로 여러 브랜치가 같은 번호를 참조하고 있으면 그쪽을 고치는 비용이 훨씬 크다.

## 3. 브랜치와 PR

### 3.1 스택 PR 은 머지만으로 재타겟되지 않는다

**규칙**: 부모 PR 을 머지한 **직후** 자식 PR 의 base 를 명령으로 옮긴다. 자동 재타겟에 기대지 않는다.

**근거**: 주요 호스팅 플랫폼의 자동 재타겟 트리거는 **머지가 아니라 "머지 후 head 브랜치 삭제"** 이고, 대상도 **열린 PR** 뿐이다. 부모 브랜치를 지우기 전에 자식을 머지하면, 자식은 이미 머지된 부모 브랜치로 들어가고 **그 변경분은 통합 브랜치에 반영되지 않는다.**

이 실패는 조용하다. 자식 PR 은 정상적으로 "머지됨" 으로 보이고, 누락은 나중에 기능이 없는 것으로 발견된다.

**실행**: 부모 머지 직후 자식의 base 를 통합 브랜치로 바꾼다. 호스팅 CLI 의 **PR 편집 명령**을 쓴다 — 로컬 브랜치의 추적 설정을 바꾸는 명령(`git branch --set-upstream-to` 등)은 PR 의 base 와 무관하므로 소용이 없다.

**보조 방어**: 저장소의 "머지 시 head 브랜치 자동 삭제" 설정을 켠다. 삭제가 자동 재타겟의 트리거이므로 백업 방어가 된다. 다만 **설정을 켠 이후의 머지부터** 적용되며, 이미 남아 있는 브랜치를 소급 정리하지는 않는다.

### 3.2 재타겟 후 충돌이 나면

자식 브랜치가 **스쿼시 머지된 부모의 원본 커밋**을 들고 있으면 충돌이 난다. 이때 부모 브랜치를 통합 브랜치에 머지해 해결하려 들면 안 된다 — 그 브랜치는 분기 이후 통합 브랜치에 들어온 다른 작업을 **되돌릴** 수 있다.

통합 브랜치에서 새 브랜치를 따고 **자식 고유 커밋만 체리픽**하는 편이 안전하다.

### 3.3 스택을 아예 만들지 않는 선택

의존 관계가 있어도 **선행 작업이 머지될 때까지 기다렸다가 통합 브랜치에서 새로 따는 것**이 가장 안전하다. 기다리는 동안에는 의존이 없는 다른 작업을 한다.

병행 세션에서는 대기 시간이 낭비가 아니다. 스택 사고 한 번의 복구 비용이 대기 비용보다 크다.

## 4. 승인 게이트와 에이전트 권한 경계

### 4.1 승인은 사람이 한다

**규칙**: 승인 게이트가 걸린 산출물에 대해 에이전트는 **제출까지만** 한다. 승인 명령을 대신 실행하지 않는다.

**근거**: 게이트의 목적은 사람이 내용을 읽고 판단하는 것이다. 에이전트가 승인까지 실행하면 게이트는 절차만 남고 의미가 사라진다. 사후 감사에서도 승인 기록이 실제 검토를 증명하지 못한다.

**실행**: 제출한 뒤 승인 대기 상태를 사람에게 알리고, 승인에 필요한 정보(대상, 요약, 실행할 명령)를 함께 전달한다. **사람이 내용을 읽고 판단을 밝힌 뒤에는** 그 결정을 기록하는 실행까지 에이전트가 해도 된다 — 판단의 주체가 사람이면 게이트는 성립한다.

### 4.2 승인 스레드가 내용 해시 기반이면

승인 대기 중 산출물을 고치면 스레드 식별자가 바뀌어 **기존 승인 요청이 무효**가 된다. 고쳤으면 새 식별자로 재제출하고, 사람에게 바뀐 식별자를 알린다.

### 4.3 도구 실행이 권한 계층에 막힐 때

에이전트 실행 환경의 권한 정책이 외부 도구 호출을 사전 차단할 수 있다. 차단 사유가 상세히 노출되지 않는 경우가 많다.

**규칙**: 우회하지 않는다. 사용자에게 보고하고 정규 경로(권한 설정 추가)로 해결한다.

**근거**: 우회는 그 권한 정책이 막으려던 것을 무력화한다. 또 차단 사유가 불명확한 상태에서 원인을 추정해 말하면 잘못된 정보가 된다 — **모르는 것은 모른다고 보고한다.**

**실행**: 차단 사실과 시도한 명령을 그대로 보고하고, 권한 설정에 넣을 내용을 제시한다. 그동안 **작업이 멈추지 않도록** 그 도구가 필요 없는 다른 경로로 진행한다.

## 5. 위임 운영

### 5.1 목표치와 실적치를 구분한다

**규칙**: "로컬 모델에 N% 위임" 같은 수치는 **목표치**와 **실적치**를 나눠 보고한다.

**근거**: 목표를 정한 것과 실제로 그만큼 위임한 것은 다르다. 구분하지 않으면 방법론의 효과를 잘못 평가하게 된다. 위임이 실제로는 거의 일어나지 않았는데 "N% 위임 체제로 돌렸다" 고 기록되면, 다음 프로젝트에서 잘못된 전제로 계획을 세운다.

**실행**: 위임한 작업 수와 전체 작업 수를 세어 보고한다. 병행이었는지 순차였는지도 밝힌다 — 백그라운드로 던져 두고 다른 일을 했다면 병행이고, 결과를 기다렸다면 순차다.

### 5.2 위임 산출물은 실행해서 검증한다

**규칙**: 위임 결과를 그대로 신뢰하지 않는다. 실행하고, 특히 **테스트는 이름이 주장하는 것을 실제로 검증하는지** 사람 또는 상위 에이전트가 확인한다.

**근거**: 위임 신뢰도 관찰에서 반복 확인된 것이 있다 — **사실 수집은 정확하나 판단과 자기검증은 신뢰할 수 없다.** 통과하는 테스트를 만드는 것과 옳은 것을 검증하는 테스트를 만드는 것은 다르다. 이름과 내용이 어긋난 테스트는 통과하므로 자동으로는 걸러지지 않는다.

문서 초안 위임에서도 같은 성질이 나타난다. **존재하지 않는 명령·환경변수·파일명을 그럴듯하게 지어내는 경우**가 있다. 형식이 맞고 문장이 자연스러워 읽기만 해서는 걸러지지 않으므로, 문서에 적힌 명령은 **실제로 그 동작을 하는지 확인**한 뒤 남긴다.

**실행**: 위임 산출물 검토 시 최소한 아래를 본다.

- 테스트 이름과 단언 내용이 일치하는가
- 문서·코드에 등장하는 명령, 옵션, 환경변수, 파일 경로가 실재하는가
- 지시에 없던 규약·산출물을 임의로 만들어내지 않았는가
- 일반화를 요청한 문서에 특정 상황의 수치가 그대로 남지 않았는가

### 5.3 지시의 스펙 오류는 위임받은 쪽 잘못이 아니다

파일 명명 규칙 같은 저장소 관례를 잘못 지시하면 산출물도 틀린다. **관례 확인은 지시하는 쪽 책임**이다. 위임 전에 기존 파일들이 어떤 규칙을 따르는지 확인해서 지시에 담는다.

## 체크리스트

착수 전:

- [ ] 자기 워크트리를 만들었고 메인 체크아웃은 비어 있는가
- [ ] 순번 자원(마이그레이션 등)을 다른 세션 브랜치까지 확인했는가
- [ ] 미리보기 데이터가 백업 사본인가, 포트가 세션 전용인가, 프록시가 그 포트를 보는가

작업 중:

- [ ] 스택을 만들지 않고 통합 브랜치에서 땄는가
- [ ] 위임 산출물을 실행해 검증했는가

머지 전후:

- [ ] 부모 머지 직후 자식 base 를 명시적으로 옮겼는가
- [ ] 승인 게이트 대상은 제출까지만 하고 사람 판단을 기다렸는가

보고:

- [ ] 위임 비율을 목표치와 실적치로 나눠 밝혔는가
- [ ] 검증하지 못한 항목을 검증한 것처럼 쓰지 않았는가
