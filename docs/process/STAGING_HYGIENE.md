## 이 문서의 목적

커밋에 들어가면 안 되는 것이 인덱스에 올라가는 것을 막는 규칙이다. 실제 사고에서 규칙을 끌어냈다.

여러 세션이 한 저장소를 동시에 작업할 때 워크트리를 쓰면, 의존성 디렉터리를 워크트리마다 새로 설치하는 대신 원본을 가리키는 **심링크로 거는 구성**이 흔하다. 그 심링크가 커밋에 섞여 통합 브랜치까지 올라간 사고가 있었다.

심링크는 커밋되면 **절대경로 문자열 한 줄**로 저장된다. 다른 사람이 받으면 그 경로는 존재하지 않고, 의존성 디렉터리 자리에 깨진 링크가 놓인다. 빌드 명령이 실행 파일을 못 찾고 죽는다.

특정 프로젝트의 구성이나 사건 기록은 담지 않는다. 어느 저장소에서도 그대로 적용할 수 있는 규칙만 쓴다.

---

## 1. 스테이징

### 1.1 디렉터리가 아니라 파일 경로로 한다

**규칙**: 스테이징은 파일 경로를 하나씩 적는다. 전체 추가 명령은 물론이고 **디렉터리 단위 추가도 금지**다.

**근거**: "전체 추가를 쓰지 않는다" 만으로는 부족하다. 디렉터리 단위 추가도 그 아래를 통째로 훑어 심링크를 딸려 넣는다.

실제 실패는 규칙이 없어서가 아니라 **규칙을 좁게 읽어서** 났다. "경로를 명시한다" 를 "전체 추가만 안 쓰면 된다" 로 읽으면 디렉터리 추가가 규칙을 지킨 것처럼 보인다. 규칙 문장에 금지 대상을 열거해 두지 않으면 이 오독이 반복된다.

**실행**:

```bash
git add src/lib/foo.js src/lib/bar.js   # O
git add src                             # X — 아래 심링크까지 딸려온다
git add -A                              # X
```

### 1.2 커밋 전에 인덱스를 모드까지 본다

**규칙**: 커밋 직전 인덱스에 무엇이 올라갔는지 **파일 모드까지** 확인한다.

**근거**: 파일명만 보면 심링크와 일반 파일이 구분되지 않는다. 심링크는 모드 `120000` 으로 구분된다.

**실행**:

```bash
git diff --cached --name-only -z | xargs -0 git ls-files -s
```

첫 컬럼이 `120000` 인 항목이 심링크다.

## 2. 검증

### 2.1 확인 명령에서 대상을 제외 필터로 걸러내지 않는다

**규칙**: 상태 확인 출력에 **제외 필터를 걸지 않는다.**

**근거**: 노이즈를 줄이려고 특정 이름을 제외하면, 확인하려던 바로 그 문제가 출력에서 지워진다. 사고 당시 스테이징 확인은 실제로 수행됐다. 다만 확인 명령에 제외 필터가 걸려 있어 문제 줄이 출력에 나오지 않았다.

**이것이 이 문서에서 가장 중요한 규칙이다.** 앞의 규칙을 어겨도 이 규칙을 지켰다면 커밋 전에 발견된다.

**실행**: 노이즈를 줄여야 하면 제외하는 방향이 아니라 **원하는 것만 보는 방향**으로 좁힌다.

```bash
git status -s | grep -v <이름>          # X — 그 이름이 문제일 때 못 본다
git status -s -- <경로> <경로>          # O — 볼 것을 지정한다
```

### 2.2 확인했다는 것과 보였다는 것을 구분한다

**규칙**: 확인 명령을 실행한 사실을 확인의 근거로 삼지 않는다. **출력에 실제로 무엇이 보였는지**를 근거로 삼는다.

**근거**: 사고 보고에 "스테이징을 확인했다" 가 그대로 남아 있으면 다음 사람은 확인 절차가 있었는데도 못 잡았다고 읽는다. 실제 원인은 출력이 가려진 것이다. 원인이 절차에 있는지 도구에 있는지가 갈린다.

## 3. 무시 규칙의 한계

### 3.1 무시 규칙만으로는 못 막는다

**규칙**: 무시 규칙을 방어 수단으로 세지 않는다. 스테이징 시점에 막는 장치를 따로 둔다.

**근거**: 두 가지 이유가 있고, **둘은 독립적이다.** 하나를 고쳐도 다른 하나가 남는다.

| 이유 | 내용 |
| --- | --- |
| 트레일링 슬래시 | 디렉터리를 뜻하는 슬래시가 붙은 무시 패턴은 디렉터리만 매칭한다. 같은 이름의 **심링크는 통과**시킨다 |
| 추적 시작 이후 | 무시 규칙은 이미 추적되기 시작한 파일에는 **아예 적용되지 않는다.** 무시 목록에 있어도 변경이 계속 잡힌다 |

**실행**: 슬래시를 떼면 첫 번째는 해결된다. 두 번째는 인덱스에서 빼야 해결된다.

```bash
node_modules/     # 심링크를 통과시킨다
node_modules      # 심링크도 막는다
```

## 4. 커밋 훅

### 4.1 훅은 마지막 방어선이지 1차가 아니다

**규칙**: 훅을 도입하되, 앞의 규칙을 훅으로 대체하지 않는다.

**근거**: 훅은 우회할 수 있고, 새 환경·새 클론에서 설정이 빠질 수 있다. 훅이 있다는 이유로 스테이징 규칙을 느슨하게 하면 훅이 빠진 환경에서 그대로 사고가 난다.

### 4.2 검사 대상은 작업 트리가 아니라 인덱스다

**규칙**: 훅은 **스테이징된 것**만 검사한다. 작업 트리를 훑지 않는다.

**근거**: 작업 트리에는 무시 대상인 심링크가 정상적으로 존재한다. 그것까지 잡으면 **아무것도 스테이징하지 않은 커밋도 막힌다.** 막아야 할 것을 막는 것보다 막지 말아야 할 것을 통과시키는 쪽이 어렵고, 오탐이 잦은 훅은 결국 제거된다.

같은 이유로 `find` 를 조건문에 그대로 쓰지 않는다. `find` 는 일치하는 항목이 하나도 없어도 종료 코드 0 을 반환한다. 아래는 **모든 커밋을 막는다.**

```bash
if find . -type l; then    # 항상 참이다
  exit 1
fi
```

**실행**: 스테이징 목록을 얻어 모드를 본다.

```bash
git diff --cached --name-only --diff-filter=AM -z \
  | xargs -0 -I{} sh -c 'git ls-files -s "{}" 2>/dev/null' \
  | awk '$1=="120000"{ print $4 }'
```

### 4.3 우회 수단을 문서에 명시한다

**규칙**: 훅을 건너뛰는 방법을 문서에 적는다.

**근거**: 숨기면 급할 때 훅 파일 자체를 지운다. 지워진 훅은 돌아오지 않지만, 한 번 건너뛴 커밋은 기록에 남는다.

### 4.4 훅은 세 가지 경우로 검증한다

**규칙**: 훅을 도입할 때 아래 셋을 **모두** 실행해 확인한다. 하나라도 빠뜨리면 검증한 것이 아니다.

| 경우 | 확인할 것 | 빠뜨리면 |
| --- | --- | --- |
| 막아야 할 것 | 대상을 스테이징하면 커밋이 막히는가 | 훅이 아무 일도 안 하는데 있다고 믿는다 |
| 막지 말아야 할 것 | 정상 파일만 스테이징하면 통과하는가 | 오탐으로 모든 커밋이 막히고, 결국 훅이 제거된다 |
| 우회 수단 | 건너뛰기 옵션이 실제로 동작하는가 | 급할 때 훅 파일을 지우게 된다 |

**근거**: 첫 번째만 확인하고 넘어가는 경우가 많다. 그러나 훅을 죽이는 것은 대개 **두 번째**다. 통과해야 할 커밋이 막히면 사람은 훅을 고치지 않고 없앤다.

**실행**: 스크래치 저장소에서 세 경우를 순서대로 돌린다. 실제 저장소에서 시험하지 않는다.

## 5. 사고 후 정리 순서

순서가 중요하다. 뒤집으면 작업 환경이 깨진다.

| 단계 | 작업 | 주의 |
| --- | --- | --- |
| 1 | 인덱스에서만 뺀다 | **작업 트리의 실체는 남긴다.** 실체까지 지우면 의존성이 사라져 빌드가 죽는다 |
| 2 | 무시 규칙에서 트레일링 슬래시를 뗀다 | 1을 하지 않으면 효과가 없다 (§3.1) |
| 3 | 같은 사고가 다른 곳에도 있는지 전체 이력을 훑는다 | 한 번 일어난 일은 대개 여러 번 일어나 있다 |
| 4 | 훅을 넣고 §4.4 세 경우로 검증한다 | |

1단계에서 실체를 지우면 이후 브랜치를 오갈 때 링크가 복구되지 않는다.

`git stash push -u` 도 같은 결과를 만든다. 심링크를 **일반 파일(경로 문자열)로 바꿔 놓는다.** 그 상태에서는 빌드가 실행 파일을 못 찾는다. 브랜치를 오가느라 stash 를 썼다면 링크를 다시 걸어야 한다.

```bash
rm -f <경로>
ln -s <원본 경로> <경로>
```
