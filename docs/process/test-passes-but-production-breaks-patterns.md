# 테스트가 통과해도 프로덕션이 깨지는 패턴

테스트 스위트 전체가 초록인데 브라우저에서 앱이 죽은 적이 있다. 그 뒤 스위트를 감사했더니 같은 성질의 구멍이 세 갈래로 정리됐다.

세 가지 모두 **테스트가 실패하지 않는다.** 그래서 커버리지 리포트로도, 통과 건수로도 드러나지 않는다. 공통점은 하나다 — **검사 대상 코드가 한 줄도 실행되지 않았는데 통과 판정이 났다.**

---

## 패턴 1. 목이 실제 모듈에 없는 이름을 갖는다

### 어떻게 통과하는가

테스트가 모듈을 목으로 갈아끼울 때, 목 객체가 실제 모듈이 내보내지 않는 이름을 갖고 있는 경우가 있다.

```js
// 실제 모듈이 내보내는 것
export const api = { get, post, put, del, raw };

// 테스트의 목
vi.mock('../lib/api', () => ({
  api: { get, post, put, delete: del },   // delete 는 실제로 없다
}));
```

화면 코드가 `api.delete(...)` 를 부르면 **목은 응답한다.** 목이 그 이름을 갖고 있기 때문이다. 테스트는 통과한다.

브라우저에서는 실제 모듈이 붙는다. `api.delete` 는 `undefined` 이므로 `TypeError` 가 난다. 그 화면의 삭제 버튼은 처음부터 한 번도 동작한 적이 없었다.

### 그 통과가 무엇을 보장하지 못하는가

목이 응답했다는 사실만 확인했다. **실제 모듈이 그 이름을 내보내는지는 아무도 보지 않았다.** 목과 실제 모듈이 어긋난 순간부터 그 테스트는 자기 목만 검증한다.

이 사고가 실제로 났을 때, 같은 파일의 다른 테스트는 이렇게 생겼었다.

```js
it('삭제는 확인을 받는다', async () => {
  await user.click(screen.getAllByText('삭제')[0]);
  expect(await screen.findByText(/함께 지워져요/)).toBeTruthy();
  expect(del).not.toHaveBeenCalled();   // 확인 전에는 안 지운다
});
```

확인창이 뜨는 것과 **확인 전에 안 지우는 것**은 검사한다. 확인 후에 실제로 지우는지는 검사하지 않는다. 그래서 삭제가 통째로 동작하지 않아도 초록이었다.

### 대응

**목이 정의한 키를 실제 모듈의 export 목록과 대조한다.** 저장소 전체에서 기계적으로 셀 수 있다.

```
vi.mock 호출 19건 중 로컬 모듈 대상 18건 → 불일치 0건
```

이 검사를 만들 때 **탐지기 자체가 먼저 틀렸다.** 첫 판은 줄 단위 파서였고, 목이 한 줄로 쓰여 있으면 통째로 놓쳤다.

```js
api: { get, post, put, delete: del },   // 한 줄짜리 객체를 파서가 못 봤다
```

이미 알고 있던 불일치 1건을 되살려 넣었더니 탐지기가 **0건을 보고했다.** 문자 단위로 깊이를 세는 방식으로 고친 뒤에야 그 1건을 잡았다.

또 하나. 짝이 되는 양성 단언을 함께 둔다. "확인 전에 안 부른다" 옆에 **"확인 후에 부른다"** 를 놓으면 기능이 통째로 빠진 상태가 드러난다.

## 패턴 2. 빈 픽스처로 렌더하거나 실행한다

### 어떻게 통과하는가

목록을 순회하는 코드는 목록이 비면 **한 줄도 돌지 않는다.** 돌지 않은 코드는 실패할 수도 없다.

```jsx
{data.items.map(item => {
  const s = computeStatus(item.used, item.limit);
  return <span>{formatStatus(s)}</span>;   // items 가 비면 여기까지 안 온다
})}
```

화면 스모크 테스트를 처음 만들었을 때 모든 엔드포인트에 빈 배열을 줬다. 8개 페이지가 전부 통과했다.

그 상태에서 `formatStatus` 의 import 를 지워 봤다. **여전히 8개 전부 통과했다.** 그 식별자가 `items.map(...)` 안에 있어서, 목록이 비면 실행 자체가 안 되기 때문이다.

### 그 통과가 무엇을 보장하지 못하는가

비어 있을 때의 동작만 확인했다. 데이터가 있을 때 그 코드가 멀쩡한지는 확인하지 않았다.

**"렌더가 안 터졌다" 와 "렌더할 것이 없었다" 는 다르다.** 통과 결과만 보면 둘이 구분되지 않는다.

### 대응

**분기가 실제로 도는 최소 데이터를 채운다.** 건수를 늘릴 필요는 없다. 한 건이면 그 코드 경로가 돈다.

```js
items: [{ name: '항목A', limit: 300000, used: 250000 }],
```

채운 뒤 같은 뮤테이션을 다시 걸면 이번에는 잡힌다.

부수 효과가 하나 더 있다. **픽스처 모양이 실제 응답과 다르면 화면이 에러로 떨어져 테스트가 실패한다.** 이것이 목과 실제 API의 어긋남을 계속 잡아 주는 장치가 된다. 실제로 스모크를 만들면서 세 군데가 이 방식으로 드러났다.

| 엔드포인트 | 착각한 모양 | 실제 |
|---|---|---|
| 가이드 문서 | JSON 객체 | 마크다운 **텍스트** |
| 파생 항목 조회 | 상위 목록과 같은 모양 | 별도 엔드포인트, 다른 스키마 |
| 중복 후보 조회 | 평평한 배열 | 항목마다 `{ transaction, confidence, ... }` |

## 패턴 3. 로딩이 걷히기 전에 단언한다

### 어떻게 통과하는가

화면이 로딩 상태에서 일찍 반환하는 구조라면, 본문 코드는 렌더 트리에 아예 들어오지 않는다.

```jsx
if (loading) return <div>로딩 중...</div>;
if (error) return <LoadError error={error} />;
// ↓ 아래가 본문. 로딩이 안 걷히면 여기는 안 돈다
```

렌더만 하고 곧바로 단언하면 **테스트는 로딩 껍데기를 보고 통과한다.**

### 그 통과가 무엇을 보장하지 못하는가

로딩 표시가 떴다는 것만 확인했다. 본문이 렌더되는지는 확인하지 않았다.

**프로덕션에서 오류가 나지 않을 수도 있다.** 이 패턴의 문제는 앱이 깨진다는 것이 아니라 **검증이 일어나지 않았다는 것**이다. 통과가 정보를 담고 있지 않다.

### 대응

로딩이 걷힐 때까지 기다린 뒤에 단언한다. 여기에 더해 **에러 화면이 아닌 것까지 함께 요구한다.**

```js
await waitFor(() => {
  expect(screen.queryByText(/로딩 중/)).toBeNull();   // 1. 본문이 돌았다
});
expect(screen.queryByText(/다시 시도/)).toBeNull();    // 2. 에러로 빠지지도 않았다
```

**둘 중 하나만 보면 다시 빈 통과로 돌아간다.** 로딩만 기다리면 응답 모양이 틀려 에러 화면이 떠도 통과하고, 에러만 보면 로딩 상태에서 그냥 통과한다.

렌더 중 터진 예외는 경계 컴포넌트로 받아 **그 테스트의 단언으로 만든다.**

```jsx
class CrashBoundary extends React.Component {
  static getDerivedStateFromError(error) { return { error }; }
  render() {
    return this.state.error
      ? <div data-testid="smoke-crash">{String(this.state.error)}</div>
      : this.props.children;
  }
}
```

경계가 없으면 러너가 "처리되지 않은 오류" 로만 보고한다. 종료 코드는 1이라 CI 는 막히지만, **어느 화면이 죽었는지가 결과에 남지 않는다.**

## 공통 원칙 — 검사 장치를 먼저 의심한다

세 패턴을 감사하면서 만든 탐지기 네 개 중 **세 개가 첫 실행에서 거짓으로 깨끗하다고 보고했다.**

| 증상 | 원인 |
|---|---|
| 알려진 불일치 1건을 0건으로 보고 | 파서가 줄 단위라 한 줄짜리 객체를 못 봄 |
| HTTP 테스트가 0건으로 집계 | 문자열 제거 정규식이 템플릿 리터럴에서 깨져 파일의 30% 를 삭제 (16,029자 → 11,388자) |
| 단위 테스트가 0건으로 집계 | 문자열을 지우니 `require("")` 가 되어 모듈 경로를 못 찾음 |

그래서 규칙은 이렇다.

**검사가 잡아야 할 것을 일부러 만들어 넣고, 그 검사가 실패하는지 본 뒤에만 결과를 믿는다.** 망가뜨리는 대상은 **검사 대상인 프로덕션 코드**다. 테스트를 망가뜨리면 아무것도 알 수 없다.

실제 적용 예다. 화면 하나에 세 가지 뮤테이션을 걸었다.

| 무엇을 망가뜨렸나 | 실패한 테스트 |
|---|---|
| 삭제 요청 호출 제거 | 2건 |
| 되살리기 호출 제거 | 1건 |
| 목록 렌더 제거 | 2건 |
| (원복) | 22건 전부 통과 |

셋 다 잡히지 않았다면 그 22건은 아무것도 지키고 있지 않다는 뜻이다.

### 오탐을 걷어내는 것도 같은 작업이다

기계적 탐지는 오탐이 많다. 블록 단위로 "대상을 안 부르는 테스트" 를 세었더니 301건이 나왔는데, 실제 결함은 **0건**이었다.

| 단계 | 남은 건수 | 걸러낸 것 |
|---|---:|---|
| 초기 | 301 | |
| JSX 사용을 호출로 인정 | 165 | 컴포넌트는 `<Name />` 으로 쓴다 |
| 동적 import 인식 | 97 | `({ a } = await import(...))` |
| 공용 셋업 스코프 반영 | 60 | `describe` 안에서 부르고 블록은 단언만 |
| 모듈 메서드 호출 인식 | 42 | `migration.up(db)` |
| 전수 수동 확인 | **0** | 스키마 검증 31건, 상수 계약 11건 |

**"0건" 을 보고하려면 그 0이 어떻게 나왔는지 함께 말할 수 있어야 한다.** 검사가 돌지 않아서 나온 0과, 돌았는데 아무것도 없어서 나온 0은 같은 숫자지만 전혀 다른 정보다.

## 정적 검사가 먼저 막을 수 있는 것

패턴 1과 2는 결국 "그 코드가 실행됐는가" 의 문제라 테스트로 잡아야 한다. 그런데 **import 를 빠뜨린 식별자**는 실행 없이도 잡힌다.

감사 당시 그 저장소의 정적 검사는 문법 확인 하나뿐이었고, 그것도 서버 코드만 보고 있었다. 린터를 넣고 규칙 두 개만 에러로 켰다.

| 규칙 | 왜 |
|---|---|
| 정의되지 않은 식별자 | 앱이 즉시 죽는다 |
| 조건부 훅 호출 | 렌더마다 순서가 달라져 즉시 죽는다 |

스타일 규칙은 켜지 않았다. 기존 파일 수백 곳이 걸리면 도입 자체가 미뤄지고, 잡음 속에서 진짜 오류가 묻힌다.

효과는 사고를 재현해 비교했다.

| 방어선 | 결과 |
|---|---|
| 린터 | `'formatStatus' is not defined` — **잡는다** |
| 문법 확인 | 통과 (클라이언트는 보지도 않음) |
| 테스트 577건 | **577 통과** — 못 잡는다 |

## 체크리스트

- [ ] 목이 정의한 키가 실제 모듈의 export 에 전부 있는가
- [ ] 목록을 순회하는 코드에 최소 한 건이 들어가는가
- [ ] 로딩이 걷힌 뒤에 단언하는가, 에러 화면이 아닌 것도 함께 보는가
- [ ] 이 테스트가 잡아야 할 결함을 일부러 넣었을 때 실패하는가
- [ ] 정적 검사가 정의되지 않은 식별자를 막고 있는가
- [ ] 보고하는 "0건" 이 검사가 돌아서 나온 값인가
