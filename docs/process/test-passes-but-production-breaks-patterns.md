# 테스트가 통과해도 프로덕션이 깨지는 패턴

테스트가 통과해도 프로덕션에서 문제 발생하는 경우가 빈번하다. 테스트가 통과한다는 것 자체가 실제 프로덕션 코드의 안정성을 보장하지 않음을 인지하고, 테스트 설계 원칙을 재검토할 필요가 있다.

## 패턴 1. 목이 실제 표면에 없는 이름을 갖는다

**왜 통과하는가**: 테스트 목이 실제 모듈에 존재하지 않는 메서드를 호출해도 테스트는 통과한다. 목이 정의된 이름을 반환하기 때문이다.

**그 통과가 무엇을 보장하지 못하는가**: 테스트가 목을 통해 메서드가 호출되었다는 사실만 확인했을 뿐, 실제 모듈이 그 메서드를 내보내는지 검증하지 않았다. 런타임에서 코드가 실행될 때 메서드가 존재하지 않아 오류가 발생하는 상황을 피할 수 없다.

**대응**: 테스트 목에 정의된 모든 메서드 이름이 실제 모듈의 export 목록과 완전히 일치하는지, 즉각적인 확인을 수행해야 한다. 목의 정의와 모듈의 실제 구현이 일치하는지 검증해야 한다.

## 패턴 2. 빈 픽스처로 렌더하거나 실행한다

**왜 통과하는가**: 데이터가 비어 있을 때 코드를 실행하면, 비어 있는 데이터를 처리하는 코드 블록이 실행되지 않아 테스트가 통과한다.

**그 통과가 무엇을 보장하지 못하는가**: 비어 있는 상태에서의 동작만 검증했을 뿐, 실제 데이터가 존재하는 상황에서의 처리 방식을 검증하지 않았다. 데이터에 따라 코드 경로가 달라지는 상황에서 문제를 감지하지 못한다.

**대응**: 테스트에서 실제 데이터가 존재할 때의 동작을 검증해야 하며, 데이터가 비워진 상태에서는 테스트를 의미 없이 통과시킨다. 적어도 한 건의 데이터가 포함된 최소한의 픽스처로 테스트를 실행해야 한다.

## 패턴 3. 로딩이 걷히기 전에 단언한다

**왜 통과하는가**: 로딩 중인 상태에서 바로 단언을 실행하면, 실제 데이터가 표시될 코드가 실행되지 않아 로딩 스피너만 표시된 상태에서 테스트가 통과한다.

**그 통과가 무엇을 보장하지 못하는가**: 로딩 중에 화면이 표시되었다는 사실만 확인했을 뿐, 실제 데이터가 렌더되었는지 검증하지 않았다. 프로덕션에서 오류가 나지 않을 수도 있다. 문제는 검증이 일어나지 않았다는 것이다.

**대응**: 로딩이 걷힌 후에 데이터가 올바르게 표시되는지 점검해야 한다. 로딩 화면이 아닌 실제 데이터가 표시되고 에러 화면이 나타나지 않는지 같이 검증해야 한다. 로딩 중에만 단언하는 테스트는 실효성을 잃는다.

## 공통 원칙

테스트 통과 건수는 품질의 지표가 될 수 없다. 반드시 테스트 대상 프로덕션 코드를 일부러 망가뜨린 뒤 그 테스트가 실패하는지 확인해야 한다. 실패하지 않는 테스트는 실제로는 아무것도 보장하지 못하는 테스트라는 뜻이다. 이를 반드시 확인한 뒤에만 테스트가 통과했다고 볼 수 있으며, 이는 테스트가 제대로 작동한다는 확실한 증거가 된다.
